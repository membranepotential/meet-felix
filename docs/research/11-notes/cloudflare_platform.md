# Cloudflare platform gotchas for meet-felix (Rust Worker + SQLite DO + KV + R2 + Workers AI + Pages front door)

All sources read on 2026-10-09 unless marked otherwise. Items marked **(older)** come from pages or posts dated before 2026. Items marked **unverified** could not be confirmed from a primary source.

Format of each gotcha: **Symptom** → cause → fix → source.

## Q1. Workers Free vs Paid: which limits bite here?

### Takeaway
On Free the hard walls are 10 ms CPU per invocation (also per DO request/WebSocket message), 100k Worker requests/day **shared with Pages Functions**, 100k DO requests/day with incoming WebSocket messages counted 20:1, 13,000 GB-s/day DO duration (≈29 object-hours at 128 MB), 1,000 KV writes/day and 1,000 KV lists/day, and 10,000 Workers AI neurons/day (≈214 minutes of Whisper-large-v3-turbo) with no overage — exceeding any of them fails with an error rather than billing. Paid ($5/month minimum) removes all of these except the per-key rate limits; DO stub calls fall into the "internal services" bucket (1,000 on Free), not the 50 external subrequests.

### Cited Findings
- **Requests, Free:** "100,000/day", resets at midnight UTC, exceeding returns Error 1027; Paid: no limit. CPU time per HTTP request: Free 10 ms, Paid 30 s default, configurable up to 5 min. Duration: "no hard limit on duration" for HTTP; cron/alarms/queues 15 min. Memory 128 MB per isolate on both plans. — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- **Subrequests:** Free "50" external and "1,000 subrequests to internal services"; Paid 10,000 by default, raisable to 10M via `limits.subrequests`. The limits page defines subrequests as "requests made with the Fetch API or to R2, KV, or D1" and does not say whether DO stub calls count. — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/); [Changelog 2026-02-11](https://developers.cloudflare.com/changelog/post/2026-02-11-subrequests-limit/) ("Workers on the free plan remain limited to 50 external subrequests" and "1000 subrequests to Cloudflare services per invocation"; which calls count is not defined)
- **Service bindings count as subrequests:** "Each request to a Worker via a Service binding counts toward your subrequest limit." Max 32 Worker invocations per request. Service binding calls "do not count towards simultaneous open connection limits" and "Service bindings don't increase costs." — [Service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/)
- **Simultaneous open connections:** 6 on both plans; "Outbound WebSocket connections also count toward this limit." — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- **Worker size:** "64 MiB uncompressed on both plans. There is no compressed size limit." — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/). Secondary coverage says the old 3 MiB (Free)/10 MiB (Paid) compressed caps were removed server-side around 2026-09-04 and Wrangler now warns against the 64 MiB uncompressed figure — [Wrangler release note via newreleases.io](https://newreleases.io/project/github/cloudflare/workers-sdk/release/wrangler@4.129.1); [releases.sh digest 2026-08-31](https://releases.sh/collections/application-platforms/digest/2026-08-31). (Official changelog entry not located; treat the "no compressed limit" wording from the limits page as authoritative.)
- **Env vars/secrets:** 64 per Worker on Free, 128 on Paid, 5 KB each. Workers per account: 100 Free / 500 Paid. Log data per request: 256 KB. — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- **Pricing table (Free / Paid):** Workers requests 100k/day / 10M then $0.30 per M; CPU 10 ms per invocation / 30M CPU-ms then $0.02 per M; DO requests 100k/day / 1M then $0.15 per M; DO duration 13,000 GB-s/day / 400k GB-s then $12.50 per M GB-s; DO SQLite rows read 5M/day / 25B; rows written 100k/day / 50M then $1 per M; DO storage 5 GB total / 5 GB-month then $0.20 per GB-month; KV reads 100k/day / 10M then $0.50 per M; KV writes, deletes, **lists each 1,000/day** / 1M then $5 per M; KV storage 1 GB; R2 10 GB-month, 1M Class A, 10M Class B free monthly, egress free; Workers Logs 200k events/day with 3-day retention / 20M per month then $0.60 per M with 7-day retention. "Only SQLite-backed objects are available on the Free plan." "WebSocket messages routed through a Worker do not count as requests"; for DOs incoming WebSocket messages are billed 20:1 and outgoing are free. — [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)
- **Pages Functions billing:** "Requests to your Functions are billed as Cloudflare Workers requests", and the example shows 50k Functions + 50k Workers requests consuming the 100k Free daily total. Static asset requests are free and unlimited. — [Pages Functions pricing](https://developers.cloudflare.com/pages/functions/pricing/)
- **DO CPU per message:** "Each incoming HTTP request or WebSocket message resets the budget" — the CPU limit (30 s default on Paid, configurable to 5 min via `limits.cpu_ms`) applies per request/message. Per-object throughput: "soft limit of 1,000 requests per second per object"; overloaded objects return an error. Received WebSocket message size: 32 MiB. Outgoing connections per DO request: 6. — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- **DO duration billing:** billed for wall-clock time while the object "is actively running or is idle in memory but unable to hibernate"; hibernation-eligible idle objects "are not billed for duration, even before the runtime has hibernated them"; billed as 128 MB per object "regardless of actual usage"; each pending I/O operation can keep the object in memory "for up to 15 minutes each"; "Calling accept() on a WebSocket in an Object will incur duration charges for the entire time the WebSocket is connected" (use the Hibernation API instead). Alarm invocations count as requests; "Each setAlarm() is billed as a single row written"; KV `get/put/delete/list` on SQLite objects "are billed as rows read and rows written"; deletes count as rows written; an empty SQLite DB is ~12 KB and metadata counts until `deleteAll()`. SQLite storage billing started January 2026. Free limits reset 00:00 UTC; "If you exceed any limit, further operations of that type fail with an error." Worked example: 100 objects × 100 hibernatable connections with ~1 s active JS per minute ≈ $20.65/month on Paid. — [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)
- **Workers AI:** "10,000 Neurons per day at no charge"; $0.011 per 1,000 Neurons above that on Paid; on Free "N/A - Upgrade to Workers Paid" and "If you exceed any one of the above limits, further operations will fail with an error." `@cf/openai/whisper` $0.0005/audio minute (41.14 neurons/min); `@cf/openai/whisper-large-v3-turbo` $0.0005/audio minute (46.63 neurons/min). — [Workers AI pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/)
- **Workers Logs:** Free 3-day retention, 200k events/day; Paid 7-day retention, 20M/month then $0.60 per M. "Beginning December 1, 2026, Workers Logs will use Cloudflare Observability pricing." — [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)
- **DO Free tier launch:** DOs became available on Free in April 2025 **(older)** — [Changelog 2025-04-07](https://developers.cloudflare.com/changelog/2025-04-07-durable-objects-free-tier/)
- **KV-backed DO classes rejected on Free:** `legacy-kv` storage in `exports` returns `free_tier_requires_sqlite`. — [DO migrations](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/)

### Inferences
- The Pages front door doubles request billing: every `/api/*` and `/ws/*` request costs one Pages Function request plus one Worker request (via the service binding) against the same 100k/day Free quota. On Free that halves the effective budget; on Paid it is 2 × $0.30 per million.
- 13,000 GB-s/day at 0.125 GB per object = 104,000 object-seconds/day ≈ 28.9 hours of non-hibernated DO time per day. A meeting object is non-hibernated while a request, alarm, or any awaited I/O (R2 put, Workers AI call) is in flight, so a one-hour meeting with a 15-minute pending Whisper call could burn a quarter of the daily budget.
- Rust hot paths run inside the 10 ms Free CPU cap per DO WebSocket message; JSON-serializing a full `RoomState` record on every message and `put`-ing it is likely to exceed 10 ms for larger rooms. Workers Paid makes this a non-issue (30 s).
- The KV "index" is at risk on Free: `list` operations are capped at 1,000/day (same as writes). Use `get` on a fixed index key rather than `list`.
- Whisper at 46.63 neurons/min: 10,000 free neurons ≈ 214 audio-minutes/day; on Paid every extra 1,000 minutes ≈ $0.51.

### Gaps
- No primary source states explicitly whether a DO stub `fetch()`/RPC call counts as an "internal" subrequest against the 1,000 limit; the Sandbox SDK docs imply DO calls are subrequests (HTTP transport "each operation counts as one subrequest") — [Sandbox limits](https://developers.cloudflare.com/sandbox/platform/limits/). Treat as "internal, 1,000 on Free" (inference).
- Whether the Free 10 ms CPU limit also applies per DO WebSocket message on Free was not stated in the DO limits page (it gives the 30 s/5 min figures for Paid); the pricing page lists "10 ms per invocation" for Free generally. Unverified for DO specifically.

## Q2. Durable Objects: hibernation, alarms, storage, jurisdiction, overload, workers-rs

### Takeaway
Hibernation discards all in-memory state and re-runs the constructor on every wake; anything that keeps a request, timer, `waitUntil`, outbound connection, or standard-API WebSocket alive blocks hibernation and keeps the duration meter running. Attachments are now 16,384 bytes (not 2,048), auto-response pairs are 2,048 chars each, alarms are at-least-once with six exponential retries, `blockConcurrencyWhile` has a 30 s timeout that resets the object, and a deploy disconnects every WebSocket. In workers-rs 0.8.x a panic aborts the whole Wasm instance unless built with `worker-build --panic-unwind`.

### Cited Findings
**Hibernation and lifecycle**
- "In-memory state is reset"; on the next event "the Durable Object is re-initialized and its `constructor` runs". Ping frames get automatic pong replies that do "not interrupt hibernation"; "The `webSocketMessage` handler is not called for control frames". "Outgoing WebSockets do not hibernate" and keep the object alive "for up to 15 minutes". "Events such as alarms, incoming requests, and scheduled callbacks prevent hibernation"; `setTimeout`/`setInterval` also prevent it. "Code updates disconnect all WebSockets." Sending many small messages "can overwhelm a single Durable Object"; batch "every 50-100ms or every 50-100 messages". — [DO WebSockets best practice](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- Lifecycle: hibernation may happen "after 10 seconds of inactivity"; non-hibernatable idle objects are evicted "after 70-140 seconds of inactivity"; hibernation requires: no `setTimeout`/`setInterval`, no unfinished I/O or `waitUntil` promise, no open outbound connection, no WebSocket standard API in use, no request/event in flight. Shutdown causes: code deploy, idle, runtime update, placement decisions. "If a request attempts to access a Durable Object's storage, it will be stopped immediately" during shutdown; runtime updates give in-flight requests "up to 30 seconds to complete"; "WebSocket requests are terminated automatically during shutdown". — [DO lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)
- Compatibility flag `durable_object_io_tasks_prevent_eviction` (default from 2026-10-01): pending I/O (service bindings, DO RPC, `ctx.waitUntil()` promises) "keeps the object in memory, up to 15 minutes per operation". — [Compatibility flags](https://developers.cloudflare.com/workers/configuration/compatibility-flags/)
- Known issues: global uniqueness is checked at event start and on storage access, so "A long-running event that never touches storage may outlive its instance" and then storage throws; code updates roll out with eventual consistency so a newer Worker can call an older DO "for seconds to minutes" (longer with gradual deployments) — keep Worker↔DO APIs compatible in both directions. `wrangler tail` delays WebSocket logs until the socket closes. `wrangler dev` alarms may fail after hot reload; restart `wrangler dev`. — [DO known issues](https://developers.cloudflare.com/durable-objects/platform/known-issues/)

**WebSocket Hibernation API numbers**
- Tags: max 10 per socket, 256 chars each; "maximum of 32,768 WebSocket connections per Durable Object". `setWebSocketAutoResponse`: request and response strings "each capped at 2,048 characters"; auto-responses update the timestamp, are sent "without waking WebSockets in hibernation and incurring billable duration charges"; `getWebSocketAutoResponseTimestamp(ws)` returns the last `Date` or `null`. `getWebSockets()` excludes disconnected sockets but may return `CLOSING` ones. `setHibernatableWebSocketEventTimeout` max 604,800,000 ms. `blockConcurrencyWhile`: "there is a 30 second timeout applied when executing the callback" — exceeding it or throwing resets the object. `abort()` resets immediately and "Application code cannot catch this error"; alarms interrupted by abort retry unless `{ retryAlarm: false }`. `waitUntil` prevents eviction up to 15 minutes. — [DO State API](https://developers.cloudflare.com/durable-objects/api/state/)
- Attachments: "Maximum serialized size is 16,384 bytes"; persist through hibernation "as long as the WebSocket remains healthy"; "If either side closes the connection, attachments are lost"; later mutations not kept unless re-serialized; for bigger data store a key in the attachment and the data in storage. — [DO WebSockets API](https://developers.cloudflare.com/durable-objects/api/websockets/) (the 2,048-byte figure in the assignment is outdated)
- Auto-response messages "add no wall-clock time and are not charged"; incoming protocol pings are free; incoming messages billed 20:1. — [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)
- `webSocketClose(ws, code, reason, wasClean)`: with compat date ≥ 2026-04-07 (`web_socket_auto_reply_to_close`) "the runtime sends the reciprocal Close frame automatically"; on earlier dates you "**must** call `ws.close(code, reason)` inside this handler" or the client sees `1006`. `webSocketError(ws, error)` is "Called by the system when a non-disconnection error occurs"; `error` is `unknown`. `alarm(alarmInfo)` gets `retryCount` and `isRetry`. — [DO base class](https://developers.cloudflare.com/durable-objects/api/base/)
- Other WebSocket flags: `websocket_close_reason_byte_limit` (default 2026-03-03): `close()` throws `SyntaxError` if the reason exceeds 123 UTF-8 bytes; `websocket_standard_binary_type` (2026-03-17) does not affect the hibernatable `webSocketMessage` handler, "which always gets `ArrayBuffer`". — [Compatibility flags](https://developers.cloudflare.com/workers/configuration/compatibility-flags/)

**Alarms**
- "guaranteed at-least-once execution"; retried with exponential backoff "starting at two second delays for up to six retries", only on uncaught exception; "Only one instance of `alarm()` will ever run at a given time"; `setAlarm()` again "will override the existing alarm"; constructor runs before the alarm handler after inactivity, so check `getAlarm()` before re-setting in the constructor; `deleteAlarm()` inside `alarm()` prevents retries only "on a best-effort basis"; `getAlarm()` returns `null` during a running alarm. Catch exceptions and reschedule yourself rather than relying on the six retries. — [DO alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)
- `deleteAll()` deletes the alarm too for compat dates ≥ 2026-02-24 (`delete_all_deletes_alarm`). — [DO storage API](https://developers.cloudflare.com/durable-objects/api/storage-api/)

**Storage, gates, atomicity**
- KV API on SQLite objects stores data in hidden table `__cf_kv`; `get/put/delete` accept up to 128 keys per call; each method is "implicitly wrapped inside a transaction"; writes with no intervening `await` are "automatically submitted atomically"; by default I/O event delivery pauses during a storage operation (`allowConcurrency: true` opts out) and outgoing messages wait for writes to flush — "If the write fails, the system will reset the Object, discard all outgoing messages, and respond to any clients with errors instead" (`allowUnconfirmed: true` opts out); un-awaited writes buffer in memory and can exceed the 128 MB limit; cursors held across `await` may observe later changes. — [DO storage API](https://developers.cloudflare.com/durable-objects/api/storage-api/)
- SQLite limits: 10 GB per object; "Key and value combined cannot exceed 2 MB"; max string/BLOB/row 2 MB; SQL statement 100 KB; 100 columns; 100 bound params. The page is inconsistent on the Free storage cap (table says 5 GB per account, FAQ says 1 GB). — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- Deployments "restart Durable Objects and clear in-memory state"; `blockConcurrencyWhile()` in the constructor "ensures no requests are delivered until initialization completes"; new KV-backed namespaces can no longer be created. — [Access DO storage](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/)

**Errors**
- "Error: Durable Object is overloaded. Too many requests queued." / "Too much data queued." / "Requests queued for too long." / "Too many requests for the same object within a 10 second window." — all set `.overloaded`; do not retry. "Your account is generating too much load on Durable Objects. Please back off and try again later." (too many new stub lookups; retry after a short wait). "Durable Object reset because its code was updated." (in-memory only; storage unaffected). "Durable Object storage operation exceeded timeout which caused object to be reset." (large `deleteAll()`; retry until success). "Your account is doing too many concurrent storage operations." (batch `get(keys[])`). "Cannot apply `--delete-class` migration to class." (remove the binding first). — [DO troubleshooting](https://developers.cloudflare.com/durable-objects/observability/troubleshooting/)
- "Connection closed: this Durable Object instance is no longer active." — reconnect/retry. — [DO error handling](https://developers.cloudflare.com/durable-objects/reference/error-handling) (surfaced via search snippet; wording as quoted by the search result)

**Jurisdiction `eu`**
- Use `env.NS.jurisdiction("eu").idFromName(name)`; "It is possible to have the same name represent different IDs in different jurisdictions" — a plain `idFromName` and the `eu` one are different objects; mismatching namespace vs id jurisdiction errors; Workers can still reach EU objects from anywhere ("The jurisdiction constraint only controls where the Durable Object itself runs and persists data"); "A DurableObjectId will be logged outside of the specified jurisdiction for billing and debugging purposes"; `ctx.id.jurisdiction` is available in alarm handlers for alarms scheduled on/after 2026-03-15. Location hints are best-effort and only the first `get()` respects them; "Durable Objects do not currently change locations after they are created." Supported jurisdictions: `eu`, `us`, `fedramp`. — [DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)
- Data Localization Suite: Durable Objects support Regional Services (jurisdiction restrictions); Workers KV: "Jurisdictional Restrictions (storage) for Workers KV pairs is not supported today"; DO/Workers logs and analytics not available outside US with Customer Metadata Boundary. — [DLS compatibility](https://developers.cloudflare.com/data-localization/compatibility/)

**workers-rs**
- "Rust panics in Workers compile with `panic=abort`, which terminates the WebAssembly instance"; `worker-build --panic-unwind` converts panics to JS exceptions (nightly prerequisites auto-installed since v0.8.1). All crates must compile to `wasm32-unknown-unknown`; no Tokio/async_std runtime. RPC support "experimental". — [workers-rs README](https://github.com/cloudflare/workers-rs); [workers-rs releases](https://github.com/cloudflare/workers-rs/releases) (v0.8.7 2025-09-25: MSRV 1.91; v0.8.6: `blockConcurrencyWhile` binding, wasm-bindgen 0.2.128, Miniflare v5; v0.8.5: "abort recovery"; v0.8.0: build output dir `pkg`→`build`, stricter `#[event]` signature validation; v0.7.5: `--panic-unwind`, AI `run_bytes`)
- `worker 0.8.7` `DurableObject` trait: `fn new(state, env)` is synchronous ("there is no async constructor" — call `State::block_concurrency_while` without awaiting), `fetch`, `alarm`, `websocket_message(ws, WebSocketIncomingMessage)`, `websocket_close(ws, code: usize, reason, was_clean)`, `websocket_error(ws, Error)`. — [docs.rs DurableObject](https://docs.rs/worker/latest/worker/durable/trait.DurableObject.html)
- `State` in 0.8.7 has `accept_web_socket`, `accept_websocket_with_tags`, `get_websockets`, `get_websockets_with_tag`, `get_tags`, `set_websocket_auto_response`, `get_websocket_auto_response`, `wait_until`, `block_concurrency_while` (gate closes at call time; `Err` terminates and resets the object; 30 s timeout; future cannot borrow `&self`), `storage`, `id`, `container`, `as_raw`. **Missing:** `get_websocket_auto_response_timestamp`, `set_hibernatable_websocket_event_timeout`, `abort` — use `as_raw()` + `wasm_bindgen` for those. — [docs.rs State](https://docs.rs/worker/latest/worker/durable/struct.State.html)
- Relevant issues: #722 "Memory leak in Rust Durable Object eviction" (closed 2025-09-26); #826 "Consider extending panic recovery to all Wasm critical errors" (open); #791 full call stacks in runtime logs (open); #812 getrandom support (closed 2025-10-31); #736 mio/getrandom feature conflicts (open); #824 worker-build 0.1.9 produced broken Workers (closed). — [workers-rs issues](https://github.com/cloudflare/workers-rs/issues?q=is%3Aissue+hibernation+OR+panic+OR+%22Date%3A%3Anow%22+OR+getrandom+sort%3Aupdated-desc)
- `getrandom` 0.4.3: `wasm32-unknown-unknown` is "not automatically supported"; enable the `wasm_js` feature (uses `Crypto.getRandomValues` via wasm-bindgen); "We strongly recommend against enabling this feature in libraries". — [docs.rs getrandom](https://docs.rs/getrandom/latest/getrandom/)

### Inferences
- The "one JSON record per meeting via `get`/`put`" design is bounded by the 2 MB key+value limit and is billed as one row read per `get` and one row written per `put`; with input gates the `put` is atomic with respect to other events only while there is no `await` between read and write — a `get` followed by an `await` on something else and then a `put` can interleave with another message (the gate reopens on non-storage awaits).
- Any `waitUntil`/pending R2 upload or Workers AI call inside the DO blocks hibernation for its duration (and keeps billing), so audio chunk uploads and transcription should either be short or moved to the Worker/RecorderObject path, not held inside the meeting object.
- Because a deploy drops every WebSocket, the client must reconnect and the DO must rebuild participants from storage plus `get_websockets()` attachments, not from memory; attachments are also lost on any close, so the stored record must remain the source of truth.
- `websocket_error` in workers-rs maps to `webSocketError` ("non-disconnection error"); whether `webSocketClose` follows it is not documented, so treat both as "socket may be dead" and reconcile via `get_websockets()`.
- With `worker` 0.8.x the `Date::now` equivalent is `worker::Date::now()` (JS `Date`), which inside a DO is frozen between I/O like any Workers clock — no source found; **unverified**.

### Gaps
- No primary source on `Response::from_websocket` or `State::accept_web_socket` doc comments (docs.rs shows no doc text), nor on `Date::now` behaviour in workers-rs.
- Whether `webSocketClose` is also delivered after `webSocketError` for the same socket — not documented.
- The "Durable Object reset" literal string appears only in the "because its code was updated" form in docs; no doc lists memory-exhaustion or uncaught-exception reset messages.

## Q3. KV

### Takeaway
KV is eventually consistent with a ~60 s window, caches negative lookups, allows one write per key per second (429 otherwise), and has a 60 s minimum expiration — fine for meeting-word → object-id lookups, but not for anything that must be visible immediately after creation at another location, and on Free the 1,000/day write and list caps are easy to hit.

### Cited Findings
- "Changes may take up to 60 seconds or more to be visible in other global network locations"; same-location visibility is usual but "it is not advised to rely on this behaviour"; "Negative lookups indicating that the key does not exist are also cached"; propagation is slower where a previous version was recently read; no atomic operations; route writes for a key through a Durable Object for write-after-write consistency. — [How KV works](https://developers.cloudflare.com/kv/concepts/how-kv-works/)
- "Workers KV has a maximum of 1 write to the same key per second"; error "KV PUT failed: 429 Too Many Requests"; `expirationTtl` minimum 60 s — "Expiration targets that are less than 60 seconds into the future are not supported"; "Expiration always takes precedence" over `cacheTtl`; "If concurrent writes are made to the same key, the last write will take precedence". Key ≤ 512 bytes, value ≤ 25 MiB, metadata ≤ 1024 bytes. — [KV write](https://developers.cloudflare.com/kv/api/write-key-value-pairs/)
- Limits: 1,000 operations per Worker invocation; minimum `cacheTtl` 30 s (default 60 s); Free: 100k reads/day, 1,000 writes/day, 1 GB storage. — [KV limits](https://developers.cloudflare.com/kv/platform/limits/); lists 1,000/day on Free — [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)

### Inferences
- A meeting word-id created in Frankfurt may be "not found" for up to 60 s for a guest whose edge location already cached the miss (e.g. a guest who tried the link before the host created it). Look the word up through the Durable Object (or retry with the DO as fallback) rather than trusting a KV miss.
- Recycling words (D6) collides with negative caching and the 60 s minimum TTL: a word freed and re-issued within a minute may resolve to the old object at some edges.

### Gaps
- List consistency is not documented on the KV pages read.

## Q4. R2 from a Durable Object

### Takeaway
R2 rate-limits writes to the same key at 1/s (429), caps custom metadata at 8,192 bytes, requires the `jurisdiction` field on the binding for an `eu` bucket, cannot mint presigned URLs through the binding (S3 SigV4 with API-token credentials is required, 7-day max expiry), and auto-aborts incomplete multipart uploads after 7 days.

### Cited Findings
- Object size 5 TiB (4.995 TiB multipart), single-part upload 5 GiB, 10,000 parts; custom metadata 8,192 bytes; "1 per second" concurrent writes to the same object name, more "will result in rate limited (429) responses"; key length 1,024 bytes; bucket management 50/s; REST API 1,200 requests per 5 minutes. — [R2 limits](https://developers.cloudflare.com/r2/platform/limits/)
- Jurisdiction `eu`: set at bucket creation (dashboard or `https://<ACCOUNT_ID>.eu.r2.cloudflarestorage.com`), immutable; Worker binding must carry `jurisdiction = "eu"` in `r2_buckets`; jurisdiction endpoints cannot access resources outside that jurisdiction; Logpush does not interact with jurisdictional buckets. Location hints honored only the first time a bucket name is created. — [R2 data location](https://developers.cloudflare.com/r2/reference/data-location/)
- Workers API: `put()` accepts `ReadableStream | ArrayBuffer | ArrayBufferView | string | null | Blob`; `onlyIf` conditional writes return `null` on failure; multipart parts "must be uniform in size with an exception for the final part"; "Uncompleted multipart uploads will be automatically aborted after 7 days"; `list()` max 1,000; `delete()` up to 1,000 keys. — [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)
- Presigned URLs: generated "server-side with no communication with R2, requiring only your R2 API credentials" (SigV4); expiry "from 1 second to 7 days (604,800 seconds)". — [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)
- Lifecycle: delete after N days or on a date; "Buckets have a default lifecycle rule to expire multipart uploads seven days after initiation"; deletions typically within 24 h; 1,000 rules per bucket; `wrangler r2 bucket lifecycle add|set|list|remove`. — [R2 lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)
- R2 Free tier: 10 GB-month, 1M Class A, 10M Class B per month; egress free. — [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)

### Inferences
- Audio chunks written at >1/s to the *same* key will 429; use one key per chunk (e.g. `meeting/<id>/<seq>.opus`) and never overwrite.
- Each R2 `put` from the DO is an I/O task that blocks hibernation and counts as a subrequest (R2 is explicitly in the subrequest definition).
- Jurisdiction-locked EU buckets need presigned URLs signed against the `eu` endpoint if the browser ever uploads directly (inference from the "jurisdiction endpoint" rule; the presigned-URL page shows only the plain endpoint).

### Gaps
- Single `put()` size limit via the binding (constrained by Worker request-body limits, numbers not on the R2 limits page) — unverified.
- Whether lifecycle rules, event notifications, or public buckets behave differently for `eu` buckets — not documented.

## Q5. Workers AI (Whisper)

### Takeaway

## Q6. Pages as a front door (service binding to the Worker)

### Takeaway
Cloudflare now says "Start new projects with Workers" (Pages docs, updated 2026-08-25), but Pages remains the only Cloudflare-hosted option for a custom domain whose DNS lives elsewhere — the migration guide lists "Custom domains outside Cloudflare zones" as unsupported on Workers. Workers Logs, gradual deployments and remote dev are Workers-only, every API/WS request is billed twice (Function + Worker), and the WebSocket pass-through over a service binding is undocumented. Cloudflare for SaaS with a Worker as origin is the documented route for custom hostnames whose DNS stays external, but it requires a separate Cloudflare zone and its plan/pricing was not confirmed.

### Cited Findings
- Pages landing page: "Are you sure you want to use Pages?" — "Workers supports most Pages use cases and offers a broader feature set"; "Start new projects with Workers." Last updated 2026-08-25. — [Pages](https://developers.cloudflare.com/pages/)
- Migration matrix: "Custom domains outside Cloudflare zones" — Workers: unsupported; Workers-only: Gradual Deployments, Remote Development, **Workers Logs**, Logpush, Tail Workers, Source Maps, Cron Triggers, Queue consumers, Rate Limiting, non-root routes. "Add a custom domain or route in Workers only if the domain's nameservers are managed by Cloudflare." "Using Durable Objects with Workers is simpler and recommended." — [Migrate from Pages](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/)
- Secondary coverage quotes a Workers tech lead that Pages-specific features are being turned into Workers features and describes Pages as "maintenance mode" — [mecanik.dev](https://mecanik.dev/en/posts/cloudflare-pages-vs-workers-which-to-use-in-2026/); [brycewray.com 2025-11](https://brycewray.com/posts/2025/11/pages-workers-again-revisited/) **(secondary)**
- Pages Functions: service binding via Wrangler config or dashboard; `context.env.SERVICE.fetch(context.request)`; dashboard-configured bindings need `wrangler pages dev --service <BINDING>=<SCRIPT>` locally; "You cannot create and deploy a Durable Object within a Pages project." — [Pages Functions bindings](https://developers.cloudflare.com/pages/functions/bindings/)
- Pages Functions billed as Workers requests against the same Free 100k/day quota; static asset requests free. — [Pages Functions pricing](https://developers.cloudflare.com/pages/functions/pricing/)
- Pages limits: 500 builds/month Free, 20,000 files per site, 25 MiB per asset, 100 custom domains per project, `_headers` 100 rules, `_redirects` 2,100 combined. — [Pages limits](https://developers.cloudflare.com/pages/platform/limits/)
- Service bindings: 32 invocations per request; counts toward subrequests; not toward open-connection limits; no cost. WebSockets and header handling are not addressed. — [Service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/)
- `CF-Connecting-IP` on same-zone `fetch()` subrequests "reflects the value of `x-real-ip`"; cross-zone subrequests set it to `2a06:98c0:3600::103`; `CF-Worker` header added to all Worker `fetch()` subrequests. Service bindings not mentioned. — [HTTP request headers](https://developers.cloudflare.com/fundamentals/reference/http-request-headers)
- **(older, 2021)** A Worker that passes a WebSocket through to another server or DO "will be billed wall-clock duration for the entire time the connection is open" (Unbound-era statement). — [Cloudflare blog: Introducing WebSockets in Workers](https://blog.cloudflare.com/introducing-websockets-in-workers)
- Workers static assets alternative: `run_worker_first` accepts up to 100 patterns, `!` negatives win, order irrelevant; on Free, over-limit `run_worker_first` requests "will receive a 429 (Too Many Requests) response instead of falling back to static asset serving"; "Requests to static assets are free and unlimited". — [Static assets binding](https://developers.cloudflare.com/workers/static-assets/binding/); [Static assets billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)
- Cloudflare for SaaS: "Add your zone to Cloudflare on a Free plan", enable SaaS, fallback origin "must be proxied", customers "set up a CNAME record at their authoritative DNS"; Worker as origin: fallback origin "only has an originless DNS record" (e.g. `AAAA 100::`), add a `*/*` Workers route; "Do not configure a custom hostname which matches the zone name." — [SaaS getting started](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/start/getting-started/); [Worker as origin](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/start/advanced-settings/worker-as-origin/)

### Inferences
- `meet.example.com` (DNS at an external provider) can be served by a Worker without moving DNS only via Cloudflare for SaaS on some *other* zone that uses Cloudflare nameservers, with `meet.example.com` CNAME'd to that zone's CNAME target and a `*/*` route to the Worker. That is the "Workers route on a custom hostname" path the question asks about; it exists but needs an additional Cloudflare-hosted zone.

### Gaps

- `cf-connecting-ip`/`request.cf` preservation over a service binding: no source.

## Q7. Observability

### Takeaway
Workers Logs must be enabled with `[observability] enabled = true` and redeployed, truncate at 256 KB per log, keep 3 days on Free / 7 on Paid, and switch to the new Cloudflare Observability pricing (0.5 GB/day Free, 50 GB per cycle Paid) on 2026-12-01; `wrangler tail` samples under load, caps at 10 viewers, and buffers WebSocket-handler logs until the socket closes.

### Cited Findings
- `observability.enabled = true` required (Wrangler ≥ 3.78.6; new Workers default on); `head_sampling_rate` 0–1; each log max 256 KB, truncated with `$cloudflare.truncated = true`; account cap 5 billion logs/day then 1% sampling. — [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)
- Observability pricing from 2026-12-01: Paid 50 GB ingestion + 12 GB-month storage per cycle, then $0.25/GB and $0.10/GB-month; Free 0.5 GB/day, 7-day retention, no overage. — [Observability pricing](https://developers.cloudflare.com/observability/pricing/)
- Real-time logs "may enter sampling mode, which means some messages will be dropped"; "A maximum of 10 clients can view a Worker's logs at one time"; `console.log` in WebSocket handlers held "until the WebSocket client closes the connection". — [Real-time logs](https://developers.cloudflare.com/workers/observability/logs/real-time-logs/)
- Jurisdiction caveat: DO ids are logged outside the jurisdiction. — [DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)

### Inferences
- Logging the serialized `RoomState` or the attachment on every message will both exceed the 200k events/day Free budget quickly and risk leaking host tokens; log event names and ids only.

### Gaps
- No doc found on redaction of secrets in Workers Logs or on `console.error` specifics inside DOs.

## Q8. Deployment: migrations, gradual deployments, compat flags, size

### Takeaway
Wrangler now offers a declarative `exports` block for DO classes (mutually exclusive with `migrations`, no `tag`, deletes are permanent with no trash, cannot be rolled back across, not gradually deployable); the compatibility dates that matter are 2026-04-07 (auto-reply to close), 2026-02-24 (`deleteAll` deletes alarm), 2026-08-04 (`nodejs_compat` default), 2026-10-01 (pending I/O prevents eviction); the Worker size limit is 64 MiB uncompressed with no compressed cap.

### Cited Findings
- `exports`: `[exports.MyDurableObject] type = "durable-object" storage = "sqlite"`; states `created|deleted|renamed|transferred|expecting-transfer`; "Deleting a class removes its namespace and **all of its stored data permanently**"; "There is no Trash"; delete blocked by other Workers' bindings (`tombstone_delete_blocked_by_external_bindings`); `exports` and `migrations` are mutually exclusive; adopt by mapping `new_sqlite_classes`→`sqlite`, `new_classes`→`legacy-kv`, remove `migrations`, deploy — and "later deploys cannot return to the `migrations` array"; "Storage type is immutable once a namespace exists"; `wrangler versions upload` fails with `exports` lifecycle changes; "Gradual deployments are not supported with `exports`"; "Rollbacks cannot cross a lifecycle change"; renames can cause brief runtime errors (three-deploy alias pattern); environments keep separate namespaces. — [DO migrations](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/)
- Gradual deployments: "only one version of each Durable Object can run at a time"; last 100 versions eligible. — [Gradual deployments](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/gradual-deployments/)
- Flags with dates: `web_socket_auto_reply_to_close` 2026-04-07; `websocket_standard_binary_type` 2026-03-17; `websocket_close_reason_byte_limit` 2026-03-03; `durable_object_io_tasks_prevent_eviction` 2026-10-01; `delete_all_deletes_alarm` 2026-02-24; `nodejs_compat`/`nodejs_compat_v2` default 2026-08-04 (v2 "larger bundle"); `fetch_iterable_type_support` 2026-02-19 (arrays as fetch bodies no longer stringified — breaking); `strip_authorization_on_cross_origin_redirect` 2025-09-01; `enhanced_error_serialization` 2026-04-21; `rpc_params_dup_stubs` 2026-01-20; `assets_navigation_prefers_asset_serving` 2025-04-01; `durable_object_fetch_requires_full_url` 2021-11-10. — [Compatibility flags](https://developers.cloudflare.com/workers/configuration/compatibility-flags/)
- Size: 64 MiB uncompressed, "There is no compressed size limit." — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Local dev: "Durable Objects ... currently will always run locally"; `wrangler dev` reads production DO storage but writes stay in memory unless `script_name` is set explicitly (then writes hit production). — [Development & testing](https://developers.cloudflare.com/workers/development-testing/); [DO known issues](https://developers.cloudflare.com/durable-objects/platform/known-issues/)
- workers-rs 0.8.0 moved worker-build output from `pkg` to `build`; 0.8.7 requires Rust 1.91. — [workers-rs releases](https://github.com/cloudflare/workers-rs/releases)

### Inferences
- A compat date ≥ 2026-04-07 removes the "must call `ws.close()` in `webSocketClose` or clients see 1006" trap; a date ≥ 2026-08-04 pulls in `nodejs_compat_v2` polyfills (bigger JS shim, irrelevant to the Wasm size).
- With `exports`, a renamed `RoomObject` class is a three-deploy operation; deleting `RecorderObject` later is irreversible.

### Gaps
- Legacy `renamed_classes`/`deleted_classes`/tag-uniqueness rules are no longer on the migrations page; only the `exports` flow is documented.
- Whether Rust Wasm counts toward the 64 MiB limit as the raw `.wasm` or after Wrangler bundling (dry-run "Total Upload") — secondary source only.
