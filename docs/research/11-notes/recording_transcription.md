# Gotchas: per-speaker recording and post-meeting transcription on Cloudflare (as of 2026-10-09)

All URLs read on 2026-10-09 unless marked. "Unverified" means I could not confirm the claim in a primary source today. The design under review: SFU WebSocket egress adapter (`location: "remote"`, `outputCodec: "pcm"`) per consenting speaker → Rust Durable Object receives protobuf `Packet` frames of 48 kHz stereo s16le → downmix + decimate to 16 kHz mono → `opus-rs` encode in 20 ms frames → Ogg/Opus chunks of ≤30 s → one R2 `put` per chunk → alarm loop sends non-silent chunks as base64 to `@cf/openai/whisper-large-v3-turbo` → merge by wall-clock into speaker paragraphs → transcript.json / transcript.md in R2 → 128-bit token link.

Existing project note with overlapping material: `docs/research/09-post-meeting-transcription-recording.md` (adapter batching, cost table, codec crate table). This note does not repeat its cost table; it adds the gotchas.

## 1. SFU WebSocket adapters (egress, `location: "remote"`)

### Takeaway
The adapter is GA since 2026-09-30, delivers 48 kHz stereo s16le per track as one WebSocket message per frame with `sequenceNumber`/`timestamp`, retries the same URL for 15 s with a short bounded audio backlog that drops old frames, and is billed as Realtime egress ($0.05/GB after a shared 1,000 GB/month free tier). The docs do not say what happens when the source track ends, what clock `timestamp` uses, whether silence/DTX produces packets, or how many bytes a frame carries; all four need a test.

### Cited Findings
- **Endpoint must be a public `wss://` URL; no custom headers; no redirects; localhost unreachable.** "Adapter requests do not support custom WebSocket headers. A scoped token in the endpoint's path or query string is one way to authenticate." The same URL is reused on reconnect, so "its credential must stay valid across retries." — [WebSocket adapter](https://developers.cloudflare.com/realtime/sfu/media-transport-adapters/websocket-adapter/)
- **Audio format:** 48 kHz, stereo, signed 16-bit little-endian, L/R interleaved. Protobuf: `message Packet { uint32 sequenceNumber = 1; uint32 timestamp = 2; bytes payload = 5; }`; "Each egress frame is a separate WebSocket message." Field numbers 3 and 4 are undefined. — [WebSocket adapter](https://developers.cloudflare.com/realtime/sfu/media-transport-adapters/websocket-adapter/)
- **`sequenceNumber` is "an incremental packet counter" in stream mode; `timestamp` is described only as "for synchronization", with no clock rate stated.** — [WebSocket adapter](https://developers.cloudflare.com/realtime/sfu/media-transport-adapters/websocket-adapter/) (via search snippet of the same page)
- **Frame size per message is not documented**; the page only says to send "small, frequent audio chunks". Max serialized message 32 KB "including protobuf overhead". — [WebSocket adapter](https://developers.cloudflare.com/realtime/sfu/media-transport-adapters/websocket-adapter/); [SFU limits](https://developers.cloudflare.com/realtime/sfu/limits/)
- **Reconnect:** "the SFU retries the same endpoint for up to 15 seconds after a disconnect"; "Audio egress uses a short, bounded backlog, and older frames are dropped when it fills"; "Recovery does not guarantee gapless or exactly-once delivery, and there is no failover to another URL"; after the window "the adapter closes. Create a new adapter to resume." — [WebSocket adapter](https://developers.cloudflare.com/realtime/sfu/media-transport-adapters/websocket-adapter/)
- The retry window was 5 s when auto-reconnect shipped on 2026-05-29 and was raised to 15 s at GA on 2026-09-30; close became idempotent at GA. — [Changelog 2026-05-29](https://developers.cloudflare.com/changelog/post/2026-05-29-websocket-adapter-auto-reconnect/index.md); [Realtime changelog](https://developers.cloudflare.com/realtime/changelog/)
- **Source track end is not described in the docs.** Related timeouts: a track with no incoming media packets for 30 s is garbage-collected; a session that loses WebRTC connectivity has a 30 s reuse window. — [SFU limits](https://developers.cloudflare.com/realtime/sfu/limits/)
- **Limits:** 1–4 track entries per create/close request; API rate limit 50 req/s per session; no documented cap on adapter count or adapter duration. — [SFU limits](https://developers.cloudflare.com/realtime/sfu/limits/)
- **Partial success:** HTTP 200 can contain failed items with `errorCode`/`errorDescription` (e.g. `websocket_handshake_failed`); if every item fails the outer status is 503; "Retrying the whole creation batch can create duplicate resources." — [WebSocket adapter](https://developers.cloudflare.com/realtime/sfu/media-transport-adapters/websocket-adapter/)
- **Billing:** SFU/TURN egress $0.05/GB, first 1,000 GB/month free, shared between SFU and TURN; adapter egress to your endpoint "follows the Realtime egress rate and shares the Realtime free tier"; ingest into the SFU is free; `bytesProcessed` on close "is not the authoritative billed-usage total". — [Realtime pricing](https://developers.cloudflare.com/realtime/sfu/platform/pricing/); [WebSocket adapter](https://developers.cloudflare.com/realtime/sfu/media-transport-adapters/websocket-adapter/)
- **Deploying new Worker code disconnects all WebSockets** because every DO restarts. — [DO WebSockets best practices](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- Cloudflare's own STT example (`ai-tts-stt`) converts the adapter's stereo 48 kHz PCM to mono 16 kHz with a SpeexDSP WASM resampler and a JS fallback, allows only one SFU audio subscriber per DO, and treats 503 `adapter_not_found` on stop as success. — [STTAdapter.md](https://github.com/cloudflare/realtime-examples/blob/main/ai-tts-stt/STTAdapter.md)

### Inferences
- Gotcha: **token in the URL is the only auth.** The SFU connects from Cloudflare's network with no headers you control. Put a per-adapter random token in the path, bind it to (meeting, participant, adapter) in DO storage, and keep it valid for the whole adapter life (reconnects reuse it). Never log the full URL.
- Gotcha: **egress volume is 6x what you store.** 48 kHz stereo s16le = 192,000 B/s = 691 MB per speaker-hour. 10 speakers x 1 h = 6.9 GB; free up to ~145 speaker-hours/month, then ~$0.035 per speaker-hour. Cheap, but it is the largest byte flow in the system and it counts against the same 1,000 GB as TURN.
- Gotcha: **a 15 s reconnect does not mean 15 s of audio is preserved.** The backlog is "short" and unspecified; expect a hole after any disconnect. Detect holes with `sequenceNumber` jumps and `timestamp` deltas, and start a new chunk after a hole instead of concatenating (otherwise wall-clock alignment drifts for the rest of the chunk).
- Gotcha: **every deploy during a meeting creates a hole in every recording** (all WebSockets drop; SFU reconnects within 15 s). Either refuse deploys while meetings run, or accept and log the hole.
- Gotcha: **the adapter probably closes silently when the publisher leaves or re-publishes.** Not documented. Key adapters by participant, watch `webSocketClose`, and create a new adapter when a participant's `sessionId`/`trackName` changes (reconnect = new track). Verify by test what close code the SFU sends.
- Gotcha: **`timestamp` clock is unknown.** If it is the RTP timestamp of the Opus track, it is a 48 kHz clock with a random start and 32-bit wrap (every ~24.9 h at 48 kHz), and it may jump when the publisher re-publishes. Do not use it as wall-clock; use the DO's `Date.now()` at the first frame of each chunk plus sample counting inside the chunk, and use `timestamp` deltas only to detect gaps. Unverified; test with a recorded session.
- Gotcha: **DTX/silence behaviour is unknown.** Browsers do not enable Opus DTX by default, so the SFU most likely decodes a continuous stream and sends PCM frames continuously (unverified). If a publisher does use DTX, the SFU could either emit PLC/zero frames or skip frames; your gap detection must treat both as silence, not as reconnect holes.
- Gotcha: **message count, not bytes, drives DO request billing.** If frames are 20 ms (3,840 B payload, unverified), that is 50 messages/s per speaker; see section 2 for cost.
- Gotcha: **batch creation with per-item errors.** Store each successful `adapterId` before retrying the failed entries; a blind retry duplicates adapters, which doubles egress and sends two streams to one endpoint.

### Gaps
- Bytes per frame (frame duration) of egress PCM: undocumented; measure.
- Behaviour on source track end / publisher reconnect / `close` by another request: undocumented.
- `timestamp` unit and continuity across reconnect: undocumented.
- Whether frames are emitted during DTX silence: undocumented.
- Maximum adapter lifetime and per-app adapter cap: not in the limits page (absence of a documented cap is not proof there is none).
- Public bug reports on the adapter in 2025–2026: I found none beyond the changelog (open beta 2025-08-29, JPEG 2025-11-21, auto-reconnect 2026-05-29, GA 2026-09-30).

## 2. Durable Object as a media sink

### Takeaway
A DO acting as the WebSocket *server* for the SFU can use the Hibernation API, but it will never actually hibernate while frames arrive, so in-memory chunk buffers survive only until eviction, crash or deploy. Memory (128 MB) is ample for a dozen speakers; message billing at 20:1 and R2 puts are cheap; the real constraints are the 6-connection subrequest limit, the lost partial chunk on restart, and the 15-minute alarm wall clock for the transcription loop.

### Cited Findings
- **Memory:** "Each isolate can consume up to 128 MB of memory, including the JavaScript heap and WebAssembly allocations." — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- **CPU:** 30 s default per request, raisable to 5 min; "Each incoming HTTP request or WebSocket message resets the remaining CPU time to 30 seconds." — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- **Incoming WebSocket message limit 32 MiB**; larger messages close the socket with code 1009. Binary frames are fully buffered before the event fires; hibernatable `webSocketMessage` handlers always get `ArrayBuffer`. The page says nothing about `bufferedAmount` or backpressure for `send()`. — [Workers WebSockets](https://developers.cloudflare.com/workers/runtime-apis/websockets/)
- **Hibernation only for incoming WebSockets:** "Outgoing WebSockets do not hibernate." Alarms, incoming requests, `setTimeout`/`setInterval` block hibernation. On hibernation "in-memory state is cleared"; per-socket attachments via `serializeAttachment` are limited to 16,384 bytes. — [DO WebSockets best practices](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- **Billing:** incoming WebSocket messages billed at 20:1; outgoing messages and protocol pings free; requests $0.15/M after 1 M/month; duration $12.50 per million GB-s after 400,000 GB-s, counted as wall clock for 128 MB per object; "Pending I/O can keep an object in memory for up to 15 minutes per operation." — [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)
- **Simultaneous open connections: 6 per invocation** (waiting on response headers); a seventh is queued. Subrequests 10,000 per invocation on Paid. — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- **Alarms:** one alarm per object; at-least-once; retried on exception with exponential backoff from 2 s, up to 6 retries; only one `alarm()` runs at a time per object; handler wall time max 15 min; "If an unexpected error terminates the Durable Object, the `alarm()` handler may be re-instantiated on another machine." — [DO alarms](https://developers.cloudflare.com/durable-objects/api/alarms/); [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- **DO storage sizes (SQLite backend):** key+value ≤ 2 MB; each row/string/BLOB ≤ 2 MB; 10 GB per object on Paid. — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- **R2:** "1 concurrent write per second to the same key", higher rates return 429; single-part upload up to 5 GiB; object key ≤ 1,024 bytes; metadata ≤ 8,192 bytes; REST management API 1,200 req per 5 min (this is the management API, not Workers binding puts). — [R2 limits](https://developers.cloudflare.com/r2/platform/limits/)
- **R2 jurisdiction and DO jurisdiction** are the EU controls for storage (Regional Services / CMB table: Durable Objects compatible with footnote "Jurisdiction restrictions"; R2 "Jurisdictional Restrictions guarantee objects in a bucket are stored within a specific jurisdiction"). — [Data localization compatibility](https://developers.cloudflare.com/data-localization/compatibility/)
- Cloudflare's STT example persists alarm deadlines and restores state in `blockConcurrencyWhile()` in the constructor, and uses `setWebSocketAutoResponse('ping','pong')`. — [STTAdapter.md](https://github.com/cloudflare/realtime-examples/blob/main/ai-tts-stt/STTAdapter.md)

### Inferences
- Gotcha: **it will not hibernate, and that is fine, but do not rely on it for persistence.** At 50 frames/s per speaker the DO has continuous incoming events; duration billing runs for the whole meeting (≈450 GB-s per hour ≈ $0.0056/h above the free 400,000 GB-s/month, i.e. ~888 free meeting-hours). Design the recorder as if it could be killed any second: a partial chunk (≤30 s of Opus ≈ 60 KB at 16 kbps) lives only in WASM memory.
- Gotcha: **lost partial chunk on eviction/crash/deploy.** Options: (a) accept up to 30 s loss per speaker per restart and record the hole in the transcript; (b) write the encoded Opus packets of the open chunk to DO SQLite every few seconds (rows ≤ 2 MB, 50 M row writes/month free) and rebuild the Ogg chunk on restart; (c) shorter chunks. (b) is cheap because Opus packets are ~40 B each at 16 kbps/20 ms; batch every 1–2 s into one row.
- Gotcha: **message billing is per message, not per byte.** At 50 msg/s per speaker: 180,000 msg/h → 9,000 billed requests per speaker-hour ≈ $0.00135 above the free 1 M/month. Ten speakers for an hour = 90,000 billed requests, i.e. 11 such meetings fit in the free tier before any cost. Not a problem, but it is the biggest "request" consumer in the app, so the 20:1 ratio matters (Cloudflare's own figure, [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)).
- Gotcha: **memory is dominated by WASM linear memory, which never shrinks.** Budget: raw 48 kHz stereo frame ~4 KB; 16 kHz mono 30 s PCM 960 KB if you keep PCM (do not: encode as you go, keep only packets); encoder state ~1 KB with `heap` feature (250 KB without) ([opus-rs README](https://docs.rs/crate/opus-rs/latest)). Even 20 speakers with 1 MB each is <25 MB. The risk is a leak or an unbounded queue, not steady state.
- Gotcha: **no `bufferedAmount` and no backpressure for inbound frames**: if the WASM step cannot keep up, messages queue inside the runtime and memory grows. Keep per-frame CPU far below 20 ms (downmix + polyphase decimation + Opus frame at complexity ≤5 should be well under 1 ms natively; wasm without SIMD is slower — measure).
- Gotcha: **R2 put from the DO is a subrequest subject to the 6-simultaneous-connection limit**; a slow R2 put while 10 speakers' chunks end at the same second queues the rest. Stagger chunk boundaries per speaker (they already differ because cuts happen at silence) and never `await` an R2 put inside the frame handler; queue puts and drain them in a separate task, persisting the queue head in storage.
- Gotcha: **the 1 write/s per key rule is per key**, so one put per 30 s per speaker key is far below it; but retries on 429/5xx must not re-put the same key within the same second.
- Gotcha: **alarm handler max 15 min wall time and single alarm per object**: a 10-speaker, 60-minute meeting is up to 1,200 chunks; at 2–5 s per Whisper call (unverified latency) sequential processing needs 40–100 min. Make the loop resumable: persist a cursor (next chunk id) before each call, process a bounded batch, `setAlarm(now)` and return. Because `alarm()` is at-least-once, the per-chunk Whisper result write must be idempotent (keyed by chunk id).
- Gotcha: **alarm retries stop after 6 failures**; a persistent 429 from Workers AI would stall the whole transcript. Catch errors inside `alarm()`, record the failure, and reschedule yourself with your own backoff instead of throwing.
- Gotcha: **deploys**: a code deploy restarts all DOs → all adapters reconnect (section 1) and any in-flight alarm is re-run on restart.

### Gaps
- Actual per-frame CPU of `opus-rs` in wasm32 (no SIMD) at 16 kHz: no benchmark found; the README benchmarks are native x86-64/aarch64.
- Whether the SFU honours TCP backpressure if the DO is slow: undocumented.
- Whether the R2 Workers binding has a per-bucket write rate limit beyond the per-key rule: not stated on the limits page.

## 3. Audio processing in WASM (decimation, Opus, Ogg, silence, chunking)

### Takeaway
Decimate 48→16 kHz with a proper low-pass (cutoff <8 kHz) using a polyphase FIR on the downmixed mono signal; encode with `Application::Voip`, 16–24 kbps VBR, complexity ~5, no DTX (do silence gating yourself); build Ogg/Opus by RFC 7845 with granule positions in 48 kHz units even though the input is 16 kHz, pre-skip from the encoder lookahead, and a terminal page per chunk. Do not rely on Ogg Opus playback on iOS older than 18.4.

### Cited Findings
- **Anti-aliasing before decimation:** decimation alone "creates undesirable aliasing"; ideal anti-aliasing cutoff is below half the new sample rate; with FIR "it is an easy matter to compute only every Mth output" (polyphase). — [Wikipedia: Downsampling](https://en.wikipedia.org/wiki/Downsampling_(signal_processing))
- Cloudflare's example uses SpeexDSP (WASM) for 48→16 kHz with a plain JS fallback. — [STTAdapter.md](https://github.com/cloudflare/realtime-examples/blob/main/ai-tts-stt/STTAdapter.md)
- **`opus-rs` 0.1.37 (2026-10-07):** "pure-Rust implementation of the Opus audio codec (RFC 6716), ported from the reference C implementation (libopus 1.6)"; no C deps; verified no_std targets include `wasm32-unknown-unknown`; `OpusEncoder::new(16000, 1, Application::Voip)`; `encode_i16` (since 0.1.34); sample rates 8/12/16/24/48 kHz; frame sizes 2.5–60 ms; settings exposed as fields `bitrate_bps`, `use_cbr`; complexity 0–10 and in-band FEC mentioned; **DTX, signal type and bandwidth CTLs are not documented**; packets capped at 1,276 bytes; encoder ~1 KB with `heap` feature, ~250 KB without; no Ogg writer mentioned; status self-described as "Production-ready"; conformance to RFC 6716 test vectors not mentioned. — [opus-rs on docs.rs](https://docs.rs/crate/opus-rs/latest)
- Note: the GitHub repo `DCNick3/opus-rs` is a different thing (libopus C bindings, crate `opus`), not the pure-Rust crate. — [DCNick3/opus-rs](https://github.com/DCNick3/opus-rs)
- **libopus encoder CTLs:** VBR on by default; constrained VBR on by default; DTX "applies only to the LPC layer", default off; complexity 0–10; `OPUS_SET_SIGNAL_VOICE` biases to SILK/Hybrid; `OPUS_APPLICATION_VOIP` "processes the signal for improved speech intelligibility"; `OPUS_GET_LOOKAHEAD` returns the codec delay in samples and "Applications needing delay compensation should call this CTL rather than hard-coding a value"; the encoder's share of the delay "can vary by implementation, version, or configuration". — [Opus encoder CTLs (1.5)](https://opus-codec.org/docs/opus_api-1.5/group__opus__encoderctls.html)
- **RFC 7845 (Ogg Opus):** granule position counts 48 kHz samples "regardless of the decoder's output rate"; pre-skip (16-bit LE) is subtracted from granule positions, "a pre-skip of at least 3,840 samples (80 ms) is RECOMMENDED to ensure complete convergence" (§5.1); input sample rate field is metadata only (16000 is fine); OpusHead alone on page 0, OpusTags ends its page, both granule 0; gaps in granule are not allowed — muxers "SHOULD emit packets that explicitly request the use of Packet Loss Concealment (PLC) in place of the missing packets", only multiples of 2.5 ms are repairable (§4.1); the first audio page's granule may exceed its sample count to allow cropping/live joining (§4.5); end trimming via the EOS page granule (§4.4); chaining segments "creates a small discontinuity at the boundary due to the lossy nature of Opus" (§7.2); a page holds ≤65,025 octets of packet data from ≤255 packets; no normative maximum page duration. — [RFC 7845](https://www.rfc-editor.org/rfc/rfc7845.html)
- **Safari:** Ogg container support for Opus and Vorbis arrived in Safari 18.4 (macOS 15.4, iOS 18.4, iPadOS 18.4, visionOS 2.4), released 2025-03-31; MediaRecorder gained WebM/Opus in the same release. — [WebKit: Safari 18.4](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)
- A May 2025 test found Safari 18.4 still cannot *record* `audio/ogg;codecs=opus` via MediaRecorder; it did not test playback. — [frequal.com, 2025-05-18](https://frequal.com/java/OggOpusStillNotWorkingInSafari18_4.html) (older item)
- **Whisper on non-speech audio (large-v3):** 40.3% of 301,317 inferences on pure non-speech produced hallucinations; by length 52.1% at 1 s, 11.6% at 10 s, 27.4% at 20 s, 62.3% at 30 s; top phrases "thank you" 24.76%, "thanks for watching" 10.32%, "subtitles by the amara org community" 0.46%; beam size 1 hallucinated least (19.5% vs 28.2% at beam 5); `hallucination_silence_threshold` helped slightly (21.3% → 14.7% at 20 s); Silero VAD cut hallucinations to 0.2% and WER from 104.8% to 8.0%; WebRTC VAD only to 12.5%. — [arXiv 2501.11378 (ICASSP 2025)](https://arxiv.org/html/2501.11378)

### Inferences
- Gotcha: **naive "take every 3rd sample" aliases everything above 8 kHz into the speech band** (fricatives, keyboard noise). Downmix to mono first (`(L+R)/2` in i32, then clamp), then a linear-phase FIR low-pass with cutoff ~7 kHz and stopband at 8 kHz, computed polyphase so you only evaluate every third output; a 48-tap-ish FIR is plenty for ASR. Avoid IIR unless you keep state per speaker across frames (you must keep FIR history across frames too: 20 ms frames of 960 input samples need the last N-1 inputs from the previous frame).
- Gotcha: **frame alignment**: 20 ms at 16 kHz = 320 samples = 960 input samples per frame; if the SFU frame size is not a multiple of 960 samples (unknown, section 1), buffer input and emit encoder frames independently of the inbound frame boundary.
- Gotcha: **`opus-rs` has no documented DTX or signal-type control** and may lack `OPUS_GET_LOOKAHEAD`. Do not plan on codec DTX; gate silence yourself before the encoder (and do not even encode fully silent frames once the chunk is closed). Measure the actual lookahead by encoding a known impulse and decoding it to find the delay, then write that (x3 to 48 kHz units) as pre-skip; or write a fixed pre-skip only after you have measured it. A wrong pre-skip shifts every timestamp by a few ms, which is harmless for ASR but wrong for playback alignment.
- Gotcha: **granule arithmetic at 16 kHz**: each 20 ms packet adds 960 (not 320) to the granule position. The EOS page's granule must equal pre-skip + 960 x packets (minus any end trim). If a chunk is cut at a silence boundary that is not a frame boundary, pad to a whole frame with zeros and trim with the EOS granule rather than emitting a short frame.
- Gotcha: **chunk start and PLC packets**: because each chunk is its own Ogg stream (OpusHead + OpusTags + audio pages + EOS), you never need RFC 7845 §4.1 PLC-request packets for the gap between chunks; but inside a chunk, if the SFU dropped frames (sequence gap), either close the chunk at the gap (recommended, keeps wall-clock honest) or insert zero frames. Never let the granule run ahead of the packet count.
- Gotcha: **don't chain Ogg streams to "join" chunks for Whisper**; Whisper gets one chunk per request anyway. Chaining is only relevant if you later offer a per-speaker download; then concatenate chunks as sequentially multiplexed segments with distinct serial numbers (RFC 7845 §9) and accept the small discontinuity.
- Gotcha: **encoder settings for ASR**: `Application::Voip`, 16 kHz mono, VBR, 20 ms frames, 20–24 kbps (16 kbps is intelligible; headroom costs ~1.5 MB/h per speaker extra). Complexity 10 is the quality default in libopus examples but costs CPU in wasm; measure at 5. Set `max bandwidth` wideband if the crate exposes it (input is already 8 kHz-limited, so it changes nothing audible but saves bits). Disable in-band FEC (no packet loss in a file).
- Gotcha: **silence detection threshold**: with s16 PCM, speech RMS is typically > -40 dBFS and room noise from a muted/quiet mic < -55 dBFS; use a frame-level energy gate with hysteresis (e.g. open at -45 dBFS, close after 500 ms below -55 dBFS, unverified rule of thumb) rather than a single RMS threshold, and prefer cutting a chunk after ≥300 ms of continuous silence so words are not clipped. Whisper has no clipping protection: a cut in the middle of a word yields a garbled token at both chunk edges; there is no overlap-merge in the design, so cut only in silence or at the 30 s limit with a short tail (e.g. extend to the next silence, up to 35 s).
- Gotcha: **silence-only chunks must never reach Whisper** (62% hallucination at 30 s of non-speech). "Non-silent" means the gate was open for at least, say, 500 ms during the chunk; also skip chunks whose Whisper response has `transcription_info.duration_after_vad` ≈ 0 when `vad_filter` is on. Post-filter the known phrases ("Thank you.", "Thanks for watching.", "Untertitel der Amara.org-Community", "Vielen Dank." etc. — the German equivalents are my extrapolation, unverified).
- Gotcha: **music/hold music or a second person laughing in the background** on a speaker's own track triggers the same hallucinations; the energy gate passes it. Accept, or use `vad_filter: true` (Cloudflare does not say which VAD it uses; faster-whisper's is Silero, which the paper found effective).
- Gotcha: **playback**: if the transcript page offers "play this segment", Ogg/Opus works in Firefox/Chrome and in Safari ≥18.4 only; iOS 17 and earlier cannot play it. Either state the requirement or transcode on demand (not in scope). WebM/Opus playback in older Safari is unverified today.

### Gaps
- `opus-rs` wasm32 CPU per 20 ms frame, lookahead value, DTX/bandwidth controls: not documented; test.
- `opus-rs` RFC 6716 test-vector conformance: not stated in README.
- Whether Workers AI's `vad_filter` is Silero (faster-whisper) or something else: not documented.
- German hallucination phrases for Whisper: no source found; the paper is English-centric.

## 4. Workers AI `@cf/openai/whisper-large-v3-turbo`

### Takeaway
Input is base64 (or a `{body, contentType}` object), output has `segments[].{start,end,text,no_speech_prob,avg_logprob,compression_ratio,words[]}` and `transcription_info.{language,language_probability,duration,duration_after_vad}`; price $0.000513/min; ASR rate limit 720 req/min; no documented size/duration cap, no documented EU inference and Workers AI is "Not compatible" with Regional Services, with CoreWeave (US) and Nebius (England) as Workers AI subprocessors.

### Cited Findings
- **Schema:** `audio` is `anyOf` [string "Base64 encoded value of the audio data", object `{body: object, contentType: string}`]; params `task` (default `transcribe`), `language`, `vad_filter` (default false), `initial_prompt`, `prefix`, `beam_size` (5), `condition_on_previous_text` (true, "Setting to false may help prevent hallucination loops"), `no_speech_threshold` (0.6), `compression_ratio_threshold` (2.4), `log_prob_threshold` (-1), `hallucination_silence_threshold` (seconds, optional). Output: `text`, `word_count`, `vtt`, `transcription_info{language, language_probability, duration, duration_after_vad}`, `segments[]{start,end,text,temperature,avg_logprob,compression_ratio,no_speech_prob,words[]{word,start,end}}`. `async_queue: "true"`. No size/duration limit in the schema. — [whisper-large-v3-turbo.json (cloudflare-docs)](https://raw.githubusercontent.com/cloudflare/cloudflare-docs/production/src/content/workers-ai-models/whisper-large-v3-turbo.json); [model page](https://developers.cloudflare.com/workers-ai/models/whisper-large-v3-turbo/)
- **Price:** $0.000513 per audio minute. — [model page](https://developers.cloudflare.com/workers-ai/models/whisper-large-v3-turbo/)

### Inferences
- Gotcha: **no documented request cap means you find it by 413/5xx in production.** A 30 s Ogg/Opus chunk at 20 kbps is ~75 KB (≈100 KB as base64), far below any plausible limit; the chunking tutorial's "memory and execution time" wording suggests the limit is on decoded audio length, not bytes. Keep chunks ≤30 s, which also matches Whisper's 30 s window so each chunk is exactly one window (no cross-window context carry-over, which also removes `condition_on_previous_text` loops).
- Gotcha: **base64 inflates size by 4/3 and costs CPU in the DO** (encode 100 KB per chunk: trivial). The `{body, contentType}` variant is undocumented beyond the schema; stick with base64, which you verified works with Ogg/Opus.
- Gotcha: **rate limit 720/min is per account**, shared with any other ASR use; with 6 simultaneous connections per DO invocation you cannot exceed ~6 in-flight calls anyway, so throughput is bounded by latency: at an assumed 2–4 s per 30 s chunk (unverified), one DO does ~100–180 chunks/min, i.e. a 10-speaker hour (≤1,200 non-silent chunks, usually far fewer because most speakers are silent most of the time) transcribes in ~7–12 min of alarm time, spread across several 15-min alarm invocations with a persisted cursor.
- Gotcha: **429/5xx handling:** Workers AI errors arrive as thrown exceptions in the binding; treat 429 as "sleep and reschedule the alarm" and 5xx as retry-with-backoff per chunk, never as alarm failure (6-retry limit, section 2). Persist per-chunk status: pending / done(text) / failed(n).
- Gotcha: **`no_speech_prob` is per segment and only meaningful together with `avg_logprob`**: OpenAI's reference logic skips a segment when `no_speech_prob > no_speech_threshold` AND `avg_logprob < log_prob_threshold` (from openai/whisper `transcribe.py`; not re-read today, unverified). Workers AI applies these thresholds server-side with the defaults above. For your merge, additionally drop segments with `no_speech_prob > 0.8`, `compression_ratio > 2.4`, or text in the hallucination list, and drop whole chunks whose `duration_after_vad` is < 0.5 s.
- Gotcha: **`beam_size` default 5 hallucinates more than 1 on noisy input** (28.2% vs 19.5% in the paper); try `beam_size: 1` or 2 for speed and fewer hallucinations, at a small accuracy cost on clean speech.
- Gotcha: **language detection is per chunk (per 30 s window)** and returns one language; a chunk that switches German→English mid-sentence gets transcribed in the detected language, with the other language's words often "translated" or phonetically mangled. Mitigations within the design: keep `language` unset (as verified), keep chunks short (per-speaker chunks are naturally monolingual more often), store `transcription_info.language` and `language_probability` per chunk for the merge, and consider `initial_prompt` with a bilingual sentence ("Dies ist ein Meeting auf Deutsch und Englisch. This meeting mixes German and English.") plus names/terms — Whisper's prompt biases spelling and language; its effect on code-switching is unverified.
- Gotcha: **`initial_prompt` is per request**, so you must send the same glossary (participant display names, product names) with every chunk; it costs nothing extra in audio minutes. Keep it short (the prompt shares the 448-token decoder context with the output in reference Whisper; unverified for the Workers AI implementation).
- Gotcha: **timestamps**: `segments[].start/end` and `words[]` are seconds relative to the chunk; absolute time = chunk wall-clock start + offset. Whisper's segment timestamps are quantised to 20 ms and can drift by ±0.5 s near silences; with ≤30 s chunks drift cannot accumulate. Word timestamps on short chunks are good enough to order interleaved speakers at sentence level, not at word level.
- Gotcha: **inference location is not the EU.** Workers AI is "Not compatible" with Regional Services and has US and England subprocessors; your DO/R2 EU jurisdiction settings do not cover the Whisper call. Legally this is a transfer to a third country (US via Cloudflare's DPA/DPF, UK adequacy); you must name it in the recording notice (section 6). Operationally, nothing you can set; if the owner wants EU-only inference, Workers AI cannot promise it (as of 2025-10-01 subprocessor list).
- Gotcha: **Nova-3 is 10x the price but has `diarize`, `keyterm`, `detect_language` and takes `encoding: opus`**; since you already have per-speaker tracks, diarization buys nothing; Nova-3 is only a fallback if Whisper's German/English switching proves unusable. Nova-3's code-switching behaviour on Workers AI is undocumented (the upstream "multi" language mode is not mentioned on the page).

### Gaps
- Max audio duration/size per request: undocumented; your 30 s chunks are safe, but "how far is too far" needs a probe.
- Per-request latency of the turbo model on Workers AI: no published figure.
- Exact server-side implementation (faster-whisper?) and which VAD: not documented.
- Whether `initial_prompt` helps or hurts German/English code-switching: no source.
- Whether the Workers AI pipeline splits a >30 s input into windows (the schema implies yes via `condition_on_previous_text`): not stated.

## 5. Transcript merging

### Takeaway
Merge is a pure function over (speaker, chunk wall-clock start, segment offsets); the hard parts are wall-clock skew between adapters, holes after reconnects, and overlapping speech. No external source covers this exact design; the findings below are inferences from sections 1 and 4 plus RFC 7845.

### Cited Findings
- Per-chunk `segments[].start/end` and `words[].start/end` are "within the audio, in seconds". — [whisper-large-v3-turbo.json](https://raw.githubusercontent.com/cloudflare/cloudflare-docs/production/src/content/workers-ai-models/whisper-large-v3-turbo.json)
- Adapter delivery after a disconnect is neither gapless nor exactly-once. — [WebSocket adapter](https://developers.cloudflare.com/realtime/sfu/media-transport-adapters/websocket-adapter/)
- Nova-3 `diarize` assigns speaker numbers per word "starting at 0" — i.e. speaker labels are numbers, not names, in the diarization alternative. — [nova-3](https://developers.cloudflare.com/workers-ai/models/nova-3/)

### Inferences
- Gotcha: **each speaker's clock is its own adapter pipeline** (publisher capture → SFU → WebSocket → DO), with latency differences of tens to hundreds of ms and jitter; wall-clock from the DO's `Date.now()` at the first frame of a chunk is accurate to roughly ±200 ms across speakers (unverified estimate). Good enough to order turns, not to interleave words. Record `t0 = Date.now()` once per chunk at its first frame, then compute every later time inside the chunk from the sample count (not from `Date.now()` again), so jitter does not accumulate.
- Gotcha: **"exactly-once" is not guaranteed**: after a reconnect the SFU may resend a frame; detect duplicates by `sequenceNumber` (same or lower than last seen) and drop them, or the chunk gets 20 ms longer than wall-clock.
- Gotcha: **holes**: when a sequence gap larger than one frame appears, close the chunk and start a new one with a fresh `t0`; otherwise everything after the hole shifts earlier in wall-clock. Store `(t0, duration_samples, had_hole_before)` per chunk; render holes in the transcript as "[Verbindung unterbrochen, 12 s]" so readers know why a sentence is missing.
- Gotcha: **overlapping speech** is normal in meetings; with per-speaker tracks each speaker's words are intact (the main advantage of this design). In the merge, do not interleave at the word level; emit speaker turns: group each speaker's consecutive segments into a turn while the gap to the next segment < ~1.5 s and the same speaker; then sort turns by start time; when two turns overlap by more than ~50% of the shorter one, keep both in start order and mark the second with "(gleichzeitig)" or an overlap flag in JSON. Paragraph breaks: new paragraph on speaker change or on a within-speaker pause > ~3 s.
- Gotcha: **duplicate display names**: participants can both be "Felix"; number them deterministically by join order ("Felix", "Felix (2)") and keep the mapping from participant id to label in transcript.json so the markdown stays stable if someone is renamed mid-meeting.
- Gotcha: **a participant who leaves and rejoins** gets a new track, adapter and (possibly) a new participant id; map by the meeting-core participant identity, not by `sessionId`, or they appear as two speakers.
- Gotcha: **chunks transcribed out of order** (parallel Whisper calls, retries) must not affect the result: merge from stored per-chunk results sorted by `t0`, never from arrival order. Write transcript.json only when all chunks are done or failed, and include the failed chunk count.
- Gotcha: **language per chunk**: record `transcription_info.language` per segment in transcript.json; the markdown does not need it, but a later re-run with `language` forced for low-probability chunks does.

### Gaps
- No published merge algorithm for per-track Whisper transcripts was found; the above is design reasoning, not sourced practice.
- Cross-speaker clock skew of the SFU adapter path: unmeasured.

## 6. Legal and privacy for Germany (recording notice, consent, token link)

### Takeaway
§ 201 StGB makes recording the non-public spoken word without consent a crime; automated transcription counts as a recording because audio is stored. Criminal law accepts implied consent (joining a clearly labelled meeting); data-protection law (Art. 6(1)(a), Art. 13 GDPR) wants an explicit, documented, informed, revocable consent with a full information notice, including the transfer to Cloudflare and its US/UK Workers AI subprocessors. Nextcloud Talk's checkbox-before-join is the closest reference pattern; the DSK's 2020 Orientierungshilfe demands recording be off by default, moderator-only, visibly indicated, encrypted at rest, and deleted promptly. A random-token link is defensible only with access controls around it (expiry, deletion, no indexing) because the guidance requires "nur berechtigte Personen".

### Cited Findings
- **§ 201 StGB:** up to three years or a fine for anyone who without authorisation records "das nichtöffentlich gesprochene Wort eines anderen auf einen Tonträger" or uses/makes accessible such a recording; attempt is punishable. — [§ 201 StGB](https://www.gesetze-im-internet.de/stgb/__201.html)
- **GDD Kurzpapier 4 "Gesprächstranskription" (Stand Januar 2026):** "Da die meisten Transkriptionstools eine Zwischenspeicherung des Audiosignals vornehmen, liegt technisch regelmäßig eine Aufnahme vor. Ohne Einwilligung aller Beteiligten ist dies strafbar." (§4). "Strafrechtlich genügt eine konkludente Zustimmung (z.B. Weiterreden trotz Hinweis auf Aufzeichnung), während datenschutzrechtlich eine ausdrückliche, dokumentierte Einwilligung erforderlich ist." (§4.2). Information must cover "den Zweck der Verarbeitung, den Umfang der Aufzeichnung und Transkription, die Speicherdauer, mögliche Empfänger sowie die eingesetzten Systeme (z.B. KI-gestützte Transkriptionssoftware)"; "bei Videokonferenzen ein Hinweis im Tool oder ein Link zur Datenschutzinformation" (§3.1). On revocation "ist die weitere Nutzung der betreffenden Aufzeichnungen oder Transkripte untersagt" and the data "müssen … unverzüglich gelöscht werden" (§3.2). "Insbesondere sollten Audioaufzeichnungen nach der Fertigstellung des Transkripts gelöscht werden" (§3.3). TOMs: "Privacy by default … keine automatische Aufzeichnung", "Zugriffskontrollen: Nur berechtigte Personen dürfen Zugriff auf Aufzeichnungen und Transkripte haben", "Audio- und Textdateien sollten verschlüsselt gespeichert und übertragen werden" (§3.4). Third country: Art. 28 AVV plus SCCs or comparable plus a check of actual protection (§3.5). Pure transcription is not high-risk AI; emotion recognition may be banned under Art. 5 KI-VO (§3.6). — [GDD Kurzpapier 4 (PDF)](https://www.gdd.de/wp-content/uploads/2026/01/GDD-Kurzpapier-4-Gespraechstranskription.pdf)
- **Heuking (2026-04-30):** automated transcription triggers § 201 StGB "regelmäßig … da technisch zumindest eine Audioaufzeichnung erfolgt"; consent "can be implied, for example by joining a labelled meeting, but only with clear and transparent information about the transcription"; the company choosing the tool is controller (citing LfDI BW); provider is processor (Art. 28); inform in the invitation and again at the start; allow objection; disable AI training and unnecessary storage. — [Heuking Fachbeitrag](https://www.heuking.de/de/news-events/newsletter-fachbeitraege/artikel/rechtssicherer-einsatz-von-ki-transkriptionstools-in-unternehmen.html)
- **DSK Orientierungshilfe Videokonferenzsysteme (Stand 23.10.2020):** recordings need a separate legal basis; "regelmäßig eine … Einwilligung in die Aufzeichnung und die weitere Verarbeitung erforderlich"; "eine etwa bestehende Aufzeichnungsfunktion [muss] in der Voreinstellung deaktiviert sein" (§3.4.8); participants are to be told "ob eine Aufzeichnung der Konferenz durch den Veranstalter möglich ist und wodurch die teilnehmenden Personen bei Aktivierung der Aufnahmefunktion auf die laufende Aufzeichnung hingewiesen werden" (§3.5); deletion of content data "regelmäßig unverzüglich nach dem Abschluss der Videokonferenz" unless a legal basis for retention exists (§3.5); recordings "nur durch besonders privilegierte Nutzer, beispielsweise Moderatoren, aktivierbar"; participants must be warned "entweder durch einen expliziten und durch die Teilnehmenden zu bestätigenden Hinweis oder durch Kennzeichnung innerhalb der Benutzerschnittstelle"; "Aufzeichnungen von Videokonferenzen sollten verschlüsselt gespeichert werden. Bei hohem Risiko ist dies zwingend" (§4.7). — [DSK OH Videokonferenzsysteme (PDF)](https://www.Datenschutzkonferenz-online.de/media/oh/20201023_oh_videokonferenzsysteme.pdf) (older item, 2020; still the current DSK guidance as far as I found)
- **Art. 13 GDPR** required content: controller identity and contact, DPO if any, purposes and legal basis, legitimate interests if Art. 6(1)(f), recipients, third-country transfer with safeguards; plus retention period or criteria, data-subject rights, right to withdraw consent, right to complain to a supervisory authority, whether provision is required, automated decision-making. — [Art. 13 DSGVO](https://dsgvo-gesetz.de/art-13-dsgvo/)
- **Cloudflare as processor:** Workers AI inputs/outputs are Customer Content, not used for training without consent. — [Workers AI data usage](https://developers.cloudflare.com/workers-ai/platform/data-usage/); subprocessors for Workers AI: CoreWeave (US), Nebius (England). — [Cloudflare sub-processors](https://www.cloudflare.com/gdpr/subprocessors/cloudflare-services/)
- **Nextcloud Talk:** admin can disable consent, require it system-wide, or let moderators set it per conversation; "every participant, including moderators, will see a highlighted section in the 'Media settings' before joining a call"; "To give explicit consent for recording, participants must check the box"; "If they do not give consent, they will not be allowed to join the call"; during recording "you will see a red indicator next to the call time"; the recording is saved to the chat as a shared file. — [Nextcloud Talk call recording](https://docs.nextcloud.com/server/stable/user_manual/en/talk/call_recording.html)
- **BigBlueButton (third-party guide):** all participants are informed when recording starts, a red pulsing indicator stays visible, optional join warning "This meeting may be recorded". — [bbbserver.com guide](https://bbbserver.com/bigbluebutton-guide/recording/recording-notifications) (secondary)
- **Jitsi:** a hosting FAQ states local recording "is not automatically communicated to the other participants and you are obliged to obtain the consent of all participants"; OpenDev added `ENABLE_LOCAL_RECORDING_NOTIFY_ALL_PARTICIPANT=true` to notify others; Jitsi Meet 26.1.1 release note "Recording notification audio updates". — [ossrox Jitsi FAQ](https://docs.ossrox.org/en/jitsi/jitsi-faq); [OpenDev commit](https://gitea10.opendev.org:3081/opendev/system-config/commit/a6e7f4bb3433b511e1fc226df34e02e0300a272e); [APKMirror 26.1.1](https://www.apkmirror.com/apk/8x8-inc/jitsi-meet/jitsi-meet-26-1-1-release) (secondary)
- Uni Göttingen: consent "muss vor Beginn der Aufzeichnung eingeholt werden"; tool-level signals (status change in BBB, thumbs-up in Zoom) can document it. — [Uni Göttingen handout](https://www.uni-goettingen.de/en/records+handout/624931.html)

### Inferences
- Gotcha: **"joining is consent" satisfies § 201 StGB only if the label is unmistakable before the audio is captured.** The join screen (not just the in-meeting banner) must state that the meeting is recorded and transcribed, who records (the host, by name), that audio goes to Cloudflare (processor) and that transcription runs on Cloudflare Workers AI with subprocessors in the US/UK, how long audio and transcript are kept, who can see the transcript (everyone with the link), and how to withdraw (leave; ask the host to delete). For GDPR the GDD wants an *explicit* act: a checkbox "Ich bin einverstanden, dass meine Stimme aufgezeichnet und transkribiert wird" on the join screen (Nextcloud pattern) is cheap and gives you a stored consent record (participant, timestamp, notice version) — store it in RoomState/DO storage and in transcript.json.
- Gotcha: **recording started mid-meeting** (host toggles after people joined): the DSK wants an explicit, confirmable notice or a UI marker; the core already broadcasts recording state (D15). Pull adapters only for participants whose consent event exists after the notice; participants who do not confirm keep talking but are not recorded, which also drops their words from the transcript — say so in the UI.
- Gotcha: **the transcript contains other people's words**, so the transcript itself is personal data of every speaker; each speaker has Art. 15/17 rights. Offer "delete this meeting's recording and transcript" to the host, and plan an automatic deletion of audio chunks once transcript.json exists (GDD §3.3) and of the transcript after a fixed period (e.g. 30 days) stated in the notice.
- Gotcha: **unguessable link vs "nur berechtigte Personen"**: 128 bits defeats guessing, but the link leaks via chat forwards, browser history, referrer headers and server logs. Minimum hygiene: `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex`, no link in logs, token only in the path (never in query strings that proxies log), link expiry (same as retention), and the host's delete button. State in the notice that anyone with the link can read it. Whether this is "defensible" is a risk judgement, not something the guidance settles; the DSK's encryption-at-rest expectation is met by R2's default encryption (Cloudflare states R2 encrypts at rest; not re-verified today, unverified).
- Gotcha: **R2/DO jurisdiction "eu" does not cover the Whisper call** (section 4). The Art. 13 notice must list the transfer; Cloudflare's DPA with SCCs/DPF is the safeguard. If the owner wants to avoid the transfer entirely, the only in-scope mitigation is to minimise what leaves: send only speech chunks (already planned), no participant names in `initial_prompt` unless needed.
- Gotcha: **private vs employment use**: the DSK/GDD texts are written for organisations; for a one-owner private tool the controller is the owner personally (household exemption does not apply once transcripts are shared with others via a link). Not legal advice.
