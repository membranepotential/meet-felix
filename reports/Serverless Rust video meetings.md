# Run Rust meetings on Cloudflare's managed SFU

*Research report, 2026-10-09. Prices and versions were checked on that date. "Unverified" marks claims that the research could not confirm from a primary source. "My estimate" marks arithmetic or design judgment that is not a cited fact.*

The best fit is this design: **Cloudflare Realtime SFU carries the media, and one Rust Durable Object (DO) per meeting handles signaling, room state, invite links and transcription control. The meeting logic is a pure Rust crate that runs both in the DO and in the browser as WebAssembly.** This keeps your Rust code out of the UDP media path, which no serverless platform hosts well. Of the options researched, it is the only one where both media and backend cost nothing while idle. The SFU bills **$0.05 per GB delivered after 1,000 free GB per month**, hibernating DOs bill no duration, and the only fixed cost is the **$5/month Workers Paid plan**. In my central estimate, a four-person hour moves about 6.7 GB and costs about **$0.34 in media** (nothing while you stay inside the free 1,000 GB). A ten-person hour costs **$1.10–2.50**. Live German and English captions add about **$0.55 per meeting-hour** with Deepgram Nova-3 on Workers AI, if audio goes to the speech-to-text (STT) service only while someone is speaking. The fallback is a self-run str0m SFU on Fly.io. Choose it if media must stay in an EU region or egress volume grows, since Fly bills $0.02/GB in Europe, but then you build simulcast handling, bandwidth adaptation and TURN integration yourself. LiveKit Cloud, Cloudflare RealtimeKit or Daily remove the media code entirely, at $0.12–0.24 per participant-hour. For the browser, a TypeScript UI that owns WebRTC and the DOM and drives a Rust WASM core carries less risk than an all-Rust Leptos UI: TypeScript has full typings for the needed browser APIs, while web-sys gates some of them behind an unstable flag and lacks others. The hard platform limit: **no phone or tablet browser can share its screen**, so mobile users can watch a screen share but cannot send one. Cloudflare also documents no EU pinning for SFU media or Workers AI, which is the main reason to keep the Fly path open.

## Cloudflare's SFU is the only media path that idles at zero without your code in it

A video meeting needs a server that receives and forwards UDP media. Serverless platforms are built for HTTP. Cloud Run's container contract lists only HTTP/1, h2c and gRPC ([Cloud Run contract](https://docs.cloud.google.com/run/docs/container-contract)). Railway staff confirm that inbound UDP is not supported ([Railway forum](https://station.railway.com/feedback/adding-inbound-udp-fad19847)). workers-rs runs without Tokio ([workers-rs README](https://github.com/cloudflare/workers-rs)), so a Rust SFU such as str0m cannot run as a Worker. The workers-rs examples folder contains a `udp-socket` example ([examples dir](https://api.github.com/repos/cloudflare/workers-rs/contents/examples)), but no source found documents an inbound UDP listener in Workers, so treat Workers as an HTTP/WebSocket-only backend (unverified). That leaves three real options: a managed SFU driven from serverless code, an SFU on a VM that you start and stop, or a managed meeting platform.

**Cloudflare Realtime SFU** forwards media tracks and DataChannels between endpoints and leaves signaling, room membership and permissions to your backend ([SFU intro](https://developers.cloudflare.com/realtime/sfu/introduction/)). Your backend calls a plain HTTPS API at `rtc.live.cloudflare.com/v1` with a bearer secret: `sessions/new`, `tracks/new`, `renegotiate`, `tracks/update` and `tracks/close` ([HTTPS API](https://developers.cloudflare.com/realtime/sfu/https-api/)). You need no SDK, so a Rust DO can drive it with `worker::Fetch`. Pricing is **$0.05/GB of egress from Cloudflare to clients; publishing is free; the first 1,000 GB per month are free and shared with TURN** ([SFU pricing](https://developers.cloudflare.com/realtime/sfu/pricing/)). The SFU supports simulcast, where each subscriber picks a layer with `preferredRid` and switches with `tracks/update` ([Simulcast](https://developers.cloudflare.com/realtime/sfu/features/simulcast/)). It forwards H.264, H.265, VP8, VP9, AV1, Opus and G.711. It allows 50 API requests per second per session and has no fixed track limit. It **garbage-collects a track that sends no packets for 30 seconds** ([Limits](https://developers.cloudflare.com/realtime/sfu/platform/limits/)). Cloudflare TURN covers clients behind strict firewalls: TURN over TLS on 443, credentials valid for up to 48 hours, and no charge for traffic between TURN and the SFU. Its relay addresses are IPv4 only and it does not support TCP relaying ([TURN FAQ](https://developers.cloudflare.com/realtime/turn/faq/)). Cloudflare's own reference app, Orange Meets, uses exactly this split of Workers + DOs + SFU ([Cloudflare blog](https://blog.cloudflare.com/orange-me2eets-we-made-an-end-to-end-encrypted-video-calling-app-and-it-was/)). The weak points are data location and recording. **You cannot choose an SFU region**, and the docs make no EU statement ([SFU intro](https://developers.cloudflare.com/realtime/sfu/introduction/)). The SFU docs list no server-side recording feature; Cloudflare offers recording only in RealtimeKit ([RealtimeKit overview](https://developers.cloudflare.com/realtime/realtimekit/)).

**A self-run str0m SFU on Fly.io Machines** is the only researched way to run your own Rust media server with near-zero idle cost. str0m 0.24.1 (2026-10-03) is a sans-IO WebRTC library: it never touches sockets or the clock, so it already has the shape of a functional core. It supports simulcast, NACK, TWCC, bandwidth estimation, data channels and ICE lite. It has **no TURN client, no adaptive jitter buffer and no PeerConnection API**, and minor releases break the API every few weeks ([str0m README](https://github.com/algesten/str0m), [crates.io](https://crates.io/api/v1/crates/str0m)). No turnkey Rust meeting server exists. The closest building blocks are young: `oxpulse-sfu-kit` (rooms and simulcast layer selection on str0m, about 1,300 downloads) ([GitHub](https://github.com/anatolykoptev/oxpulse-sfu-kit)), webrtc-rs's sans-IO `sfu` crate 0.5.0 ([GitHub](https://github.com/webrtc-rs/sfu)), and PulseBeam, which is AGPL ([GitHub](https://github.com/PulseBeamDev/pulsebeam)). Galene, a Go SFU of about 7,000 lines that handles roughly 20 meeting participants per core, shows the size of the job ([galene.org](https://galene.org/)). On Fly, UDP needs a **dedicated IPv4 ($2/month)**. The app must bind to `fly-global-services`, and the external port must equal the internal port because Fly rewrites only the IP ([Fly UDP docs](https://docs.fly.io/networking/udp-and-tcp)). One single-port str0m socket with the public IPv4 advertised as its host candidate fits these rules (my estimate; test it early). A July 2026 report shows LiveKit's SFU working on Fly once the bind was fixed ([community post](https://community.fly.io/t/running-livekit-livekit-server-livekit-sip-on-fly-the-fly-global-services-udp-bind-requirement-and-a-specific-fix/28316)). Fly bills Machines per second while they run (shared-cpu-2x about $0.0186/h at the iad price; the EU price is unverified). Stopped Machines cost only $0.15/GB-month of root filesystem, and egress in Europe costs $0.02/GB ([Fly pricing](https://docs.fly.io/about/pricing), [Fly billing](https://docs.fly.io/about/billing)). A stopped Machine boots in "well under a second" ([Machines overview](https://docs.fly.io/machines/overview)). However, Fly's autostart is a proxy feature, and no source says that UDP traffic triggers it ([autostop docs](https://docs.fly.io/launch/autostop-autostart)). The signaling backend should therefore call `POST /v1/apps/{app}/machines/{id}/start`, wait with `/wait?state=started`, and only then give clients the ICE address ([Machines API](https://docs.fly.io/machines/api/machines-resource)). Use stop, not suspend: a resume from suspend is not guaranteed, and the docs say nothing about UDP sockets after a resume ([suspend docs](https://docs.fly.io/reference/suspend-resume)). Fly's VP of Engineering stated on 2026-08-03 that Machines are "not getting wound down" ([community thread](https://community.fly.io/t/will-the-apps-and-machine-platform-start-winding-down/28380)). Fly GPUs, however, were deprecated as of July 31, 2026 ([community thread](https://community.fly.io/t/gpu-migration-fly-io-gpus-will-be-deprecated-as-of-july-31-2026/27110)). Other VM clouds fit worse. Hetzner bills servers "independent of their state" until you delete them ([Hetzner FAQ](https://docs.hetzner.com/cloud/billing/faq/)). GCE and Scaleway stop compute billing for stopped VMs but keep billing disks and IPs, and their start times were not measured ([GCE stop/start](https://docs.cloud.google.com/compute/docs/instances/stop-start-instance), [Scaleway states](https://www.scaleway.com/en/docs/instances/reference-content/instance-states.md)).

**Managed platforms** trade the Rust media layer for per-minute bills. LiveKit is the strongest of them, because the same Apache-2.0 Go server can later run on your own VM ([LiveKit](https://github.com/livekit/livekit)) and Rust client SDKs exist ([rust-sdks](https://api.github.com/repos/livekit/rust-sdks)). Its Build plan is free with 5,000 minutes and 50 GB per month; Ship costs $50/month, then $0.0005/min and $0.12/GB. The research tool mapped the pricing columns partly by inference, so re-check them ([LiveKit pricing](https://livekit.com/pricing)). Daily and 100ms list **$0.004 per participant-minute** after 10,000 free minutes ([Daily](https://www.daily.co/pricing/video-sdk/), [100ms](https://www.100ms.live/pricing)). Cloudflare RealtimeKit charges $0.002 per participant-minute and adds a UI kit, recording to R2 and transcription on Workers AI, but it ties the client to its TypeScript SDKs ([RealtimeKit pricing](https://developers.cloudflare.com/realtime/realtimekit/pricing/)).

|---|---|---|---|

## A pure Rust room core runs inside a hibernating Durable Object

The Rust side of the Cloudflare path is smaller than it looks, and it is the part that benefits most from a functional core. **workers-rs (crate `worker` 0.8.7) exposes the full DO WebSocket Hibernation API**: `State::accept_web_socket`, tagged sockets, `set_websocket_auto_response`, and the trait handlers `websocket_message`, `websocket_close`, `websocket_error` and `alarm` ([durable.rs](https://raw.githubusercontent.com/cloudflare/workers-rs/main/worker/src/durable.rs), [PR #436](https://github.com/cloudflare/workers-rs/pull/436)). These signatures were read on `main`, not on the 0.8.7 tag, and Rust access to `serialize_attachment` is unverified. The README still warns of "rough edges, some unimplemented APIs" ([workers-rs](https://github.com/cloudflare/workers-rs)), and a PR for eager memory release on hibernation is still open ([PR #832](https://github.com/cloudflare/workers-rs/pull/832)). Hibernation matters for cost: **idle hibernating DOs are not billed for duration**, while a socket accepted without the Hibernation API bills duration for the whole connection. Each incoming WebSocket message counts as 1/20 of a request, and outgoing messages are free ([DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)). After hibernation the runtime rebuilds the object, so per-connection data must live in socket attachments of at most 16,384 bytes or in storage ([DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)).

This is where the functional core pays off. Keep a `meeting-core` crate with no I/O. It holds a serializable `RoomState` and a pure function `step(RoomState, Event) -> (RoomState, Vec<Effect>)`. Events are participant messages, SFU responses, alarms and transcript fragments. Effects are values such as "call SFU `tracks/new`", "send this message to that socket", "persist", "set alarm" and "start transcription for this track". The DO is the imperative shell: it loads state from SQLite storage (`state.storage().sql()`), calls `step`, and executes the effects (my design). Because the state is one serializable value, waking from hibernation means loading and deserializing it. Because `step` is pure, you can test join, leave, lobby and renegotiation sequences with property tests and no network. The same crate compiles for the browser, so client and server share message types and validation. The str0m path reuses it unchanged, since str0m's `Rtc` is also sans-IO: an axum shell on Fly would feed the same `step` function ([str0m README](https://github.com/algesten/str0m)). That makes the hosting choice reversible at the shell level.

The SFU has no concept of rooms or participants, so the DO must track which session and track names each participant publishes. Cloudflare's own video-room example uses "one Durable Object per room for membership and track discovery" ([video-room example](https://developers.cloudflare.com/realtime/sfu/examples/video-room/)). Give each participant **separate publish and subscribe sessions**, which the SFU supports ([SFU overview](https://developers.cloudflare.com/realtime/sfu/calls-vs-sfus/)). The client then always makes the offer on its publish connection, and the backend always makes the offer on the subscribe connection, so the two sides never send offers at the same time (my design recommendation). Use the 30-second garbage collection as a design rule: a turned-off camera either keeps sending packets or must be published again when turned back on. Test which of the two your target browsers do (my estimate).

**Invite links** should copy the link-plus-knock model of Google Meet and Whereby. Meet lets hosts turn off "ask to join", keeps a guest admit queue, and blocks a knocker after two rejections ([Workspace Updates](https://workspaceupdates.googleblog.com/2026/02/safeguarded-guest-admit-flow-in-google-meet.html)). Whereby gives hosts a separate `hostRoomUrl` that carries a room key and can enter locked rooms ([Whereby waiting rooms](https://docs.whereby.com/whereby-product-features/waiting-rooms)). My recommended design: an unguessable meeting ID of at least 128 random bits in the guest link, a separate host secret, a knock queue held in the room DO, and a lobby switch that the host controls. The DO design has one advantage over LiveKit, whose self-hosted JWTs cannot be revoked ([LiveKit tokens](https://docs.livekit.io/frontends/authentication/tokens/)): the DO holds every socket, so removing someone means closing their socket and their SFU tracks at once. For data location, `jurisdiction("eu")` pins where a DO runs and stores data, but this works only with IDs from `unique_id()`, not `id_from_name` ([DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/), [durable.rs](https://raw.githubusercontent.com/cloudflare/workers-rs/main/worker/src/durable.rs)). An EU-pinned meeting link must therefore carry the DO ID itself, or a lookup must map a short code to it (my estimate). Cloudflare states general GDPR compliance under the EU Cloud Code of Conduct ([Data localization FAQ](https://developers.cloudflare.com/data-localization/faq/)), but it documents no regional guarantee for SFU media or Workers AI audio.

## Per-speaker Nova-3 streams cover German and English

The established pattern is to tap each participant's audio at the SFU and stream it to an STT service. Each stream then belongs to exactly one speaker, so you need no speaker separation (diarization). LiveKit Agents opens one STT stream per subscribed audio track ([LiveKit STT docs](https://docs.livekit.io/agents/models/stt/)). Jitsi deprecated its hidden-participant transcriber in July 2026. Its bridge now streams each participant's Opus audio, tagged by source, over one WebSocket to a transcription proxy that can be deployed to Cloudflare ([Jitsi blog](https://jitsi.org/blog/a-new-architecture-for-transcription-and-more/)).

Cloudflare made this tap official. The **SFU WebSocket adapter has been GA since 2026-09-30**. Any WebSocket server, including a DO, can receive live call audio as PCM ([SFU changelog](https://developers.cloudflare.com/realtime/sfu/platform/changelog/)). You create an adapter with one REST call. It streams 1–4 tracks as 48 kHz stereo 16-bit PCM in protobuf `Packet` messages of at most 32 KB. It needs a public `wss://` endpoint with authentication in the URL, because custom headers are not allowed, and it retries a dropped egress connection for 15 seconds ([WebSocket adapter](https://developers.cloudflare.com/realtime/sfu/media-transport-adapters/websocket-adapter/)). Cloudflare's experimental `ai-tts-stt` example builds the whole chain: SFU, adapter, an STT DO, Workers AI Nova-3, and transcript WebSocket to browsers. It resamples to 16 kHz mono, batches 100–500 ms of audio, sends a KeepAlive every 5 seconds and reconnects through DO alarms ([AI audio example](https://developers.cloudflare.com/realtime/sfu/examples/ai-audio/), [config.ts](https://raw.githubusercontent.com/cloudflare/realtime-examples/main/ai-tts-stt/src/shared/config.ts)). Its endpoints are unauthenticated, so do not copy it as is. The DO opens the Nova-3 socket with an outbound `fetch` carrying `Upgrade: websocket` ([stt-adapter.ts](https://raw.githubusercontent.com/cloudflare/realtime-examples/main/ai-tts-stt/src/stt-adapter.ts)). A Rust port needs a protobuf decoder such as prost and a resampler compiled to WASM (my estimate). Two DO rules shape the design. **Outgoing WebSockets do not hibernate**, so an STT DO stays in memory during the meeting. That costs about $0.006 per DO-hour (0.128 GB × 3,600 s × $12.50 per million GB-s), well inside the 400,000 GB-s included each month ([DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)). And the DO limits page lists **6 simultaneous outgoing connections per request** ([DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)). Whether that cap applies to long-lived sockets is unverified. Running one STT DO per speaker, as the example does, avoids the question.

For German, Deepgram lists Nova-3 support for `de` and `de-CH`, and German within its `multi` code-switching set ([Deepgram languages](https://developers.deepgram.com/docs/models-languages-overview)). Workers AI's Nova-3 accepts `language`, `detect_language`, `interim_results` and `endpointing` ([Nova-3 model page](https://developers.cloudflare.com/workers-ai/models/nova-3/)). Per-speaker streams let each participant choose German or English for their own stream. Whether Workers AI passes `language=multi` through for mixed German and English speech is unverified. Flux lists no languages and is probably English-only (unverified), so do not use it here ([Flux model page](https://developers.cloudflare.com/workers-ai/models/flux/)).

|---|---|---|---|---|---|
| Workers AI Nova-3, WebSocket | $0.55 ([Nova-3](https://developers.cloudflare.com/workers-ai/models/nova-3/)) | Yes (Deepgram list) | Yes | Not documented | One account and bill; official SFU example |
| Deepgram Nova-3 direct | $0.29 single language, $0.35 multi; promotional rates ([Deepgram pricing](https://deepgram.com/pricing)) | Yes | Yes | Not checked | Same protocol, about 40% cheaper |

| Workers AI Whisper large-v3-turbo | $0.03 ([Workers AI pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/)) | Yes (multilingual Whisper) | No, chunked request/response | Not documented | Final captions per utterance, a few seconds late |

The table hides the biggest cost lever. Streaming everyone continuously costs N × the hourly rate. In most meetings, though, one person speaks at a time. **If the STT DO forwards audio only while voice-activity detection (VAD) hears speech, a meeting sends roughly one hour of audio per meeting-hour, whatever N is** (my estimate; add a short pre-roll buffer so that first syllables are not lost). That brings Nova-3 on Workers AI to about $0.55 per meeting-hour, versus $2.21 ungated for four people. Whether Deepgram bills KeepAlive time between utterances is unverified. AssemblyAI bills open session time, so gating saves money there only if you close and reopen sockets.

The other routes are weaker for this goal. Chrome's Web Speech API sends microphone audio to Google, Firefox ships it only behind a flag, and on-device mode (`processLocally`) is experimental ([AssemblyAI blog](https://www.assemblyai.com/blog/speech-recognition-javascript-web-speech-api), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition/processLocally)). In-browser Whisper needs a model download of about 200 MB plus WebGPU ([Habr](https://habr.com/en/articles/850284/)). Moonshine's non-English models are non-streaming and under a non-commercial license ([Moonshine](https://github.com/usefulsensors/moonshine)). Self-hosted CPU transcription in Rust works through the official `sherpa-onnx` crate 1.13.8 ([crates.io](https://crates.io/api/v1/crates/sherpa-onnx)). Its only German streaming model is a Kroko zipformer with an unclear license, and NVIDIA's Parakeet TDT 0.6B v3 (CC BY 4.0, German WER about 5% on FLEURS) runs offline only ([sherpa-onnx models](https://github.com/k2-fsa/sherpa-onnx/releases/expanded_assets/asr-models), [Parakeet v3 model card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3)). The only CPU benchmark found is English: real-time factor 0.067 for one stream on six cores ([Softcery](https://softcery.com/lab/hosting-nemotron-asr-streaming-on-a-cpu)). whisper-rs has moved from GitHub to Codeberg ([whisper-rs](https://github.com/tazz4843/whisper-rs)). GPUs that scale to zero cost $0.58–0.80 per GPU-hour and have 30–120 s cold starts by third-party estimates ([RunPod](https://docs.runpod.io/serverless/pricing), [Modal T4](https://modal.com/blog/nvidia-t4-price-article)), which makes them a poor fit for one small meeting at a time. **Recommendation:** use Nova-3, called from one STT DO per speaker and gated by VAD. Start with the Workers AI endpoint, because it needs no second vendor and Cloudflare ships a working example. Keep the provider behind a Rust trait, so you can switch to Deepgram direct for lower cost or to AssemblyAI's EU endpoint for data location once its German streaming quality is tested.

## A TypeScript shell around a Rust WASM core beats an all-Rust UI

The framework choice matters less than it seems, because **every Rust UI framework reaches WebRTC through the same web-sys bindings**. Leptos 0.8.22 (2026-10-05) is the most active option, with fine-grained signals that suit many independently updating participant tiles. Dioxus's 0.8 line is still alpha, Yew 0.23 is pre-1.0 and VDOM-based, and Sycamore is small ([Leptos](https://crates.io/api/v1/crates/leptos), [Dioxus releases](https://github.com/DioxusLabs/dioxus/releases), [Yew](https://github.com/yewstack/yew)). No maintained Rust video-call client exists to learn from; the GitHub search found only one- and two-star Leptos repos ([GitHub search](https://api.github.com/search/repositories?q=leptos+webrtc)). The core RTCPeerConnection, transceiver, `sendEncodings`, `getUserMedia` and `getDisplayMedia` bindings are stable in web-sys. But `scalabilityMode`, Wake Lock, encoded transforms and `MediaStreamTrackProcessor` sit behind `--cfg=web_sys_unstable_apis` ([web-sys unstable IDL](https://github.com/wasm-bindgen/wasm-bindgen/tree/main/crates/web-sys/webidls/unstable)). `MediaStreamTrack.contentHint`, the setting that keeps screen-share text sharp, seems to be missing entirely (based on a grep of [MediaStreamTrack.webidl](https://raw.githubusercontent.com/wasm-bindgen/wasm-bindgen/main/crates/web-sys/webidls/enabled/MediaStreamTrack.webidl); confirm in a spike). Each gap means `js_sys::Reflect` calls or a JavaScript shim.

**Recommendation:** write the UI in TypeScript (Svelte is a reasonable choice; its WASM loading through Vite was not researched). Let it own the DOM, `RTCPeerConnection` and the media devices, and have it call the same `meeting-core` crate compiled to WASM for client session state, protocol types, layout and simulcast-layer choice. Share types through `tsify` 0.5.8, which generates `.d.ts` files for types that cross the WASM boundary, or through `ts-rs` 12.0.1 for type generation only ([tsify](https://crates.io/api/v1/crates/tsify), [ts-rs](https://crates.io/api/v1/crates/ts-rs)). The language boundary then sits exactly at the functional-core boundary: Rust decides, TypeScript performs the I/O. Browser APIs and iOS workarounds stay where their documentation and typings live. The cost is two toolchains. If an all-Rust client is a hard requirement, use Leptos 0.8 in client-side rendering mode, pinned until 0.9 is stable. Set the unstable cfg flag in `.cargo/config.toml`, and put the media layer in a framework-independent crate so the decision stays reversible ([Leptos releases](https://github.com/leptos-rs/leptos/releases)). Either way, ship a small WASM module: Safari 26 added an in-place WASM interpreter for faster start-up of large modules ([Safari 26.0 notes](https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes.md)), but phones still pay for download and compile time.

## Phones join and watch, but only desktops share screens

The browser matrix limits the feature list more than any server choice does. **`getDisplayMedia` is unsupported on iOS Safari, Chrome Android, Firefox Android and Samsung Internet.** Desktop Chrome 72+, Edge 79+, Firefox 66+ and Safari 13+ support it, behind a user gesture and with permission requested again each time ([MDN getDisplayMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia)). Twilio confirms that mobile browsers cannot share screens and that you need native SDKs for that ([Twilio docs](https://www.twilio.com/docs/video/screen-share-chrome)). Safari 26.x and 27.0 do not change this ([WebKit Safari 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/)). All iOS browsers use WebKit ([Ant Media](https://antmedia.io/webrtc-browser-support/)), so Chrome on an iPad behaves like Safari. Detect the feature and hide the share button. Do not try to detect the browser from its user agent, because Safari 26 reports a frozen iOS version ([Safari 26.0 notes](https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes.md)).

| Choose speaker (`setSinkId`) | Chrome 49, Firefox 116, Safari 18.4 | iOS 18.4 | No |
| Video Picture-in-Picture | Yes; Document PiP only Chrome 116, Firefox 151 | iOS 13.4, video only | Chrome Android 105 |
| Web Push for invites | Yes | Only home-screen web apps, iOS 16.4+ | Yes |

Sources for the table: [MDN getDisplayMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia), [WebKit bug 254545](https://webkit.org/b/254545), [WebKit Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [WebKit bug 232599](https://bugs.webkit.org/show_bug.cgi?id=232599), and the MDN browser-compat-data 8.1.5 set cited in the notes.

iOS needs the most defensive code. Older WebKit bugs report capture muted or ended after backgrounding, signaling sockets dead after about 30 seconds, and microphones lost after phone calls ([WebKit 226163](https://bugs.webkit.org/show_bug.cgi?id=226163), [WebKit 247994](https://bugs.webkit.org/show_bug.cgi?id=247994)). These bugs date from 2019–2023, so behavior on iOS 26/27 is unverified. The shell must handle `visibilitychange` and track `mute`/`ended` events, then reacquire the camera with `getUserMedia` plus `replaceTrack`, and reconnect signaling. iOS 26 opens every site added to the home screen as a web app by default ([WebKit Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)). Home-screen apps have a history of camera bugs, and an iOS 26 forum report describes rotated camera output in them ([WebKit 273938](https://bugs.webkit.org/show_bug.cgi?id=273938), [Apple forum](https://developer.apple.com/forums/thread/801146)). So **make invite links open and work in a normal Safari tab**, and treat the installable app as optional, useful for push notifications. Inline video needs `playsinline` ([Ant Media](https://antmedia.io/webrtc-browser-support/)).

For codecs, the SFU forwards packets without transcoding, so every subscriber must be able to decode what a publisher sends. H.264 is the only codec with hardware support on every platform, including all iOS devices, and VP8 is the universal software fallback ([Ant Media](https://antmedia.io/webrtc-browser-support/)). Safari has a working WebRTC VP9 ([WebKit STP 120](https://webkit.org/blog/11548/release-notes-for-safari-technology-preview-120/)), but AV1 is reported "supported" yet neither smooth nor power-efficient on an iPhone 15 Pro running iOS 26.4 ([WebKit bug 311593](https://bugs.webkit.org/show_bug.cgi?id=311593)). Negotiate H.264 with VP8 as the fallback, and skip AV1. Simulcast is described as limited in Safari ([Ant Media](https://antmedia.io/webrtc-browser-support/)), so test three `rid` layers from an iPhone before relying on them.

## A four-person hour costs about $0.34 in media

SFU egress dominates the bill, and egress depends on bitrates that no research note measured. Jitsi's sizing guide gives about **200 kbit/s for 180p, 500 kbit/s for 360p and 2.5 Mbit/s for 720p** per stream ([Jitsi requirements](https://jitsi.github.io/handbook/docs/devops-guide/devops-guide-requirements/)). My central assumption is an average of 1.2 Mbit/s per received camera stream (a mix of large and small tiles), 40 kbit/s audio and 1.5 Mbit/s for a screen share. Each participant receives every other participant's stream. The low ten-person case assumes 360p thumbnails at 500 kbit/s. Egress in GB per hour equals the total Mbit/s × 0.45. ## Five unverified points decide the first spike

The recommendation rests on a few points that only a prototype can settle. Each of them is cheap to test before the main build.

| Open point | Why it matters | How to test |
|---|---|---|
| Rust DO hibernation on `worker` 0.8.7, incl. `serialize_attachment` | Hibernation is what keeps the backend's idle cost at zero | Build a room DO, connect 10 sockets, and check that it hibernates (no duration on the bill) and wakes with its state intact |
| VAD gating with Nova-3 KeepAlive | Decides whether STT costs ~$0.55 or N × $0.55 per hour | Stream one meeting with gating, then compare billed audio minutes with meeting minutes |
| German or `multi` through the Workers AI Nova-3 endpoint | The language requirement | Send German and mixed German/English test audio through Workers AI and Deepgram direct and compare the transcripts |
| iPhone and iPad behavior on Safari 26/27 | Simulcast from iOS, background capture, home-screen camera | Run the call on real devices: lock the screen, switch apps, take a phone call |
| SFU egress per real meeting | Every cost figure above rests on assumed bitrates | Read the Cloudflare usage after a few real meetings |

If EU-only media turns out to be a hard requirement, add a sixth spike: str0m on a Fly Machine in Frankfurt, with one UDP port bound to `fly-global-services`, started through the Machines API from the DO.

## Conclusion

The question assumed that "serverless Rust" means running Rust in the media path. The research points the other way. **Serverless is achievable precisely because Rust stays out of the media path**: Cloudflare runs the UDP-heavy, quality-critical forwarding, and Rust owns what benefits most from types and purity, namely room state, admission, negotiation and transcription control. Writing that logic as one pure `step` function makes it a portable asset. The same crate runs in a Durable Object today, in the browser as WASM, and behind an axum and str0m shell on Fly if data location or egress prices force a move. Only the shell changes.

Cost follows the same logic. Media is cheap at small scale, often free inside Cloudflare's 1,000 GB, and transcription becomes the largest variable cost unless you gate it by speech. Gating makes STT cost roughly flat per meeting-hour instead of growing with the number of participants. The real limits on a "Google Meet clone" are set by browsers, not servers: phones cannot share screens and iOS stops capture in the background. A web-only product should plan around those limits instead of trying to fix them.
